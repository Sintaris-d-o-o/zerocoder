# Отчёт: сравнение FAISS и ChromaDB

## Как сравнивали

На одних и тех же 102 чанках документов (см. `data/Ювелир/`, после удаления одного файла-
дубля — см. раздел ниже) и одних и тех же эмбеддингах (модель
`paraphrase-multilingual-MiniLM-L12-v2`) построены два одинаковых по смыслу индекса — один в
FAISS, другой в ChromaDB. Через них прогнаны 5 тестовых вопросов (4 из задания + 1
регрессионный, добавленный после разбора реальной ошибки — см. ниже), для каждого замерено
полное время ответа (поиск + генерация локальной моделью Llama 3.2) и вручную проверена
релевантность найденных фрагментов. Полные ответы и найденные фрагменты — в
[tests/test-results.md](tests/test-results.md).

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Скорость поиска | Практически одинаковая на этом объёме данных (124 чанка) — разница во времени ответа объясняется генерацией LLM, а не поиском | Практически одинаковая |

| Персистентность (сохранение на диск) | Работает, но потребовала кастомной сериализации (см. ниже) | Работает "из коробки" (SQLite-файл + папка коллекции) |

### Важный технический нюанс: FAISS и пути с кириллицей на Windows

Стандартный способ сохранения FAISS-индекса (`store.save_local(...)`) не заработал в этом
проекте, потому что путь к папке содержит кириллицу (`C:\Проекты\...`) — библиотека FAISS
написана на C++ и открывает файлы способом, не поддерживающим не-ASCII пути на Windows.
Пришлось сохранять индекс через сериализацию в память и запись обычными средствами Python
(подробности — в `src/vector_store.py`, функция `_save_faiss_local`). ChromaDB с тем же
путём никаких проблем не создала — её персистентность работает через SQLite, к которому
Python обращается напрямую, без таких ограничений.

### Найденный баг: ChromaDB накапливала дубли при пересборке

При разборе реального вопроса пользователя («как ухаживать за изделиями из янтаря?»), на
который бот ответил «информация не найдена», хотя нужный текст в базе есть, обнаружились
две проблемы:

1. **Дубль в исходных данных.** Два файла («носка.docx» и «уход.txt») содержали абсолютно
   одинаковый текст. При `TOP_K = 4` (сколько фрагментов текста показывается модели) три
   места из четырёх занимал один и тот же общий текст «как ухаживать за украшениями» из
   трёх разных файлов, а единственный фрагмент с прямым ответом про янтарь оставался за
   бортом. Один из дублирующих файлов удалили, `TOP_K` увеличили до 8.
2. **Баг пересборки ChromaDB.** Функция `Chroma.from_documents(..., persist_directory=...)`
   не заменяет существующую на диске коллекцию, а **дописывает** в неё поверх старых данных.
   После нескольких пересборок базы (по мере правок в документах) в коллекции ChromaDB
   оказалось 350 фрагментов вместо положенных ~100 — включая фрагменты уже удалённых или
   переименованных файлов. Из-за этого качество поиска в ChromaDB со временем деградировало
   сильнее, чем в FAISS (которая при пересборке полностью перезаписывает индекс). Исправлено
   в `src/vector_store.py`: перед сборкой коллекция ChromaDB теперь полностью удаляется
   с диска.

После обоих исправлений вопрос про янтарь отвечается по существу на обеих базах — подробности
в [tests/test-results.md](tests/test-results.md).

## Вывод

На объёме данных этого задания (124 чанка, одна ниша "ювелирные изделия") FAISS и ChromaDB
находят **одинаковые по релевантности фрагменты** — что ожидаемо, так как оба используют
одни и те же векторы (эмбеддинги) и похожий принцип поиска ближайших соседей. Разница во
времени ответа между базами несущественна и в пределах погрешности измерения (обе — в
среднем около 18-19 секунд, при этом большую часть времени занимает генерация ответа
локальной моделью, а не сам поиск).

Главное отличие на практике — не качество поиска, а удобство использования:
**ChromaDB оказалась удобнее** для этого проекта, так как её персистентность (сохранение на
диск и загрузка обратно) работает "из коробки" без дополнительного кода, тогда как для FAISS
потребовался обходной путь из-за особенностей C++-библиотеки на Windows с не-ASCII путями.
Для очень больших объёмов данных (десятки/сотни тысяч документов) FAISS обычно быстрее за
счёт более эффективных алгоритмов приближённого поиска, но для задачи такого масштаба
(консультант по ювелирным изделиям с несколькими документами) это преимущество не проявилось.
