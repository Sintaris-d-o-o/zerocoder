# Развёртывание Perr7.1 (рабочие заметки)

## Сервис распознавания речи (STT)

Развёрнут на `SSH_HOST` (сервер, где также крутится n8n и бот «Тарис»), в отдельной от продакшн-бота папке и под другой учётной записью (`inna`), чтобы ничего не сломать в рабочем сервисе.

- Папка на сервере: `~/perr71-stt/` (venv + `stt_service.py`, см. копию в этой папке репозитория)
- Модель: `faster-whisper` (`small`), переиспользует уже скачанный кэш моделей бота «Тарис» (`HF_HUB_CACHE=/opt/taris-docker/data/whisper/hub`, только чтение) — новую модель не качали
- Порт: `8098` (порт `8099` уже занят другим сервисом на сервере — `sintaris-rag`)
- Слушает `0.0.0.0` (не только `127.0.0.1`) — n8n работает в отдельной docker-сети и не видит хостовый `127.0.0.1` напрямую (подробности ниже). Доступ закрыт токеном (`PERR71_STT_TOKEN`, заголовок `X-Perr71-Token`) — без него `/transcribe` отвечает 401.
- Запуск: `PERR71_STT_TOKEN=... nohup ./venv/bin/python -m uvicorn stt_service:app --host 0.0.0.0 --port 8098 > service.log 2>&1 &`
- Тяжёлые операции (ffmpeg, сама транскрибация) обёрнуты в `asyncio.to_thread` с жёстким лимитом времени (`PERR71_MAX_PROCESSING_SECONDS`, по умолчанию 240с) — иначе один долгий файл блокировал весь процесс целиком, включая `/health` (см. проблему №5 ниже).
- Проверено на всех 6 тестовых записях из `data/`: распознавание быстрее реального времени на коротких файлах, до ~4 минут на самых длинных.

## Пройденные проблемы (для истории)

1. **IMAP-вход не работал обычным паролем** — решено: создан App Password на `stani.devstar@gmail.com` (первый email `aloe.zdorovje@gmail.com` не смог включить App Passwords — недоступно для аккаунта, вероятно нет 2FA).
2. **Google Sheets OAuth 403/redirect_uri_mismatch** — решено: пользователь добавил `https://automata.dev2null.de/rest/oauth2-credential/callback` в Authorized redirect URIs нового OAuth-клиента и добавил себя в Test users OAuth consent screen.
3. **IMAP-триггер терял параметры (`downloadAttachments` и др.) при пересохранении через UI n8n** — похоже на баг/особенность UI для этого типа/версии узла: при сохранении через интерфейс параметры, совпадающие со значениями по умолчанию, не сериализуются и пропадают из JSON. Восстановлено через прямой API-вызов (PUT) и подтверждено round-trip'ом GET→PUT→GET, что значения держатся при обновлении через API. **Важно:** больше не открывать/сохранять узел «Новое письмо со звонком» через UI без проверки, что «Download Attachments» включён — иначе может снова слететь.
4. **Сетевой режим n8n (Docker) — подтверждено: отдельная docker-сеть.** `http://127.0.0.1:8098` из n8n не работал («connection refused»/«incorrect host» для `host.docker.internal`) — n8n действительно в docker-контейнере с bridge-сетью, а не в host-сети. Решение: наш сервис слушает `0.0.0.0` (см. выше), а в сценарии используется адрес шлюза docker-моста `172.17.0.1` — с хоста подтверждено, что этот адрес реально достижим из контейнера n8n (сначала было "connection refused" — сеть доходит, порт просто не слушал везде; после переключения на `0.0.0.0` заработало). Тот же адрес используется и для Ollama (`http://172.17.0.1:11434`) — она тоже слушает достаточно широко, отдельно ничего перенастраивать не пришлось.
5. **Сервис распознавания речи "зависал" насмерть на одном из файлов.** Код исходно вызывал `model.transcribe()` и `subprocess.run(ffmpeg)` синхронно прямо в async-обработчике FastAPI — это блокирует весь однопоточный event loop целиком: пока идёт одна транскрибация, сервис не отвечает вообще ни на что, включая `/health`. На одном из тестовых файлов обработка растянулась на 14+ минут (методом исключения — не конкретный размер файла, а что-то в его содержимом, видимо для faster-whisper с `beam_size` по умолчанию и `vad_filter=True` на некоторых записях возможно зацикливание, похоже на историю с Ollama из Perr6.5). Исправлено: тяжёлые вызовы вынесены в `asyncio.to_thread` с жёстким таймаутом (`asyncio.wait_for`, 240с) — сервис теперь не виснет насмерть, а корректно отвечает ошибкой 504, если файл не уложился в лимit; заодно переключили декодирование на `beam_size=1, vad_filter=False` (проще и стабильнее для этой модели).
6. **n8n обрабатывает несколько новых писем одним выполнением — и одна ошибка валит все items разом.** IMAP-триггер, если письма пришли одно за другим, может забрать сразу несколько в ОДНО выполнение сценария (until — до 6 сразу в нашем тесте). Если хотя бы один item падает на узле без `continueOnFail`, всё выполнение помечается ошибкой, и ни один item (даже уже успешно обработанный) не доходит до записи в таблицу. Из-за этого пришлось повторно прогонять записи по одной, с паузами, чтобы точно понять, какая именно падает. Итоговый сценарий это не чинит автоматически (не включали `continueOnFail`, чтобы явно видеть сбои при доработке) — при регулярной эксплуатации стоит либо развести письма по времени, либо включить продолжение при ошибке на связанных узлах.
7. **Таймаут анализа Ollama (90с) не хватало на реальных, не самых коротких транскриптах** — 3 из 6 первых прогонов падали именно на этом узле с «connection was aborted», хотя распознавание речи уже отработало. Увеличено до 300с; после этого все 6 записей прошли до конца.

## Текущий статус

Сценарий собран, **активен** в n8n и **полностью протестирован на всех 6 записях из `data/`** — каждая успешно прошла весь путь (письмо → распознавание → GPT + локальная модель → строка в таблице). Финальные параметры (URL `172.17.0.1`, таймауты 280с/300с, токен на STT-сервисе) сохранены в `Perr7.1/n8n-workflow.json` (токен в файле репозитория заменён плейсхолдером, реальное значение — только в `.env`).

Мелкий известный нюанс: в процессе отладки в таблицу успели попасть 1-2 дополнительные строки с более старыми/дублирующими данными (до того как были исправлены имя файла/отправитель и сетевые адреса) — см. `результаты.md` за инструкцией, как их отличить от финальных чистых строк.
