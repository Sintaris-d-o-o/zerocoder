# Уроки из прошлых заданий

Сюда добавляются короткие заметки после каждого задания: что пошло не так и как это исправить в будущем, либо какой приём хорошо сработал. Формат записи:

```
## <номер-задания> — <короткий заголовок урока>
Что случилось / что сработало.
Как применять в следующий раз.
```

## Perr3.5 — httpx/telegram логируют токен бота в открытом виде
При стандартном `logging.basicConfig(level=INFO)` библиотеки `httpx` и `python-telegram-bot`
пишут в лог полный URL HTTP-запроса, а URL Telegram Bot API включает сам токен бота
(`https://api.telegram.org/bot<TOKEN>/...`). Токен утекает в лог-файлы в открытом виде,
даже если нигде в коде явно не печатается.

Как применять: в любом Telegram-боте на `python-telegram-bot`/`httpx` сразу после
`logging.basicConfig(...)` поднимать уровень логов до WARNING для логгеров `httpx` и
`telegram` (`logging.getLogger("httpx").setLevel(logging.WARNING)` и аналогично для
`telegram`), чтобы токен не оседал в логах/файлах.

## Perr3.5 — отправка голосового/аудио ответа в Telegram иногда обрывается по тайм-ауту
При реальном тесте на живой сети (не в лаборатории) `reply_audio()` изредка падал с
`telegram.error.TimedOut`/`httpx.ReadTimeout`, хотя вся дорогая часть (запросы к OpenAI,
генерация аудио) уже успешно завершилась — терялся только последний шаг доставки.
Обидно терять уже готовый результат из-за сетевого дребезга на "последней миле".

Как применять: для любой отправки крупного файла (аудио/видео/документ) пользователю
в конце пайплайна — оборачивать именно этот вызов в одну повторную попытку (try/except
с retry), а не весь пайплайн целиком; если не получилось даже со второй попытки —
пользователю должно прийти хотя бы текстовое уведомление, что результат готов, но
не доставлен полностью, а не полная тишина.

## Общее — ссылки на university.zerocoder.ru требуют авторизации, WebFetch их не видит
Страницы уроков на `university.zerocoder.ru/pl/teach/control/lesson/view?id=...` закрыты
логином (платформа GetCourse). WebFetch без авторизации получает только страницу входа,
а не содержимое урока — попытка "перейти по ссылке и изучить материал" напрямую не сработает.

Как применять: при получении ссылки на урок/задание zerocoder сразу (без пробной попытки
WebFetch) просить пользователя предоставить текст урока и домашнего задания — вставить
текст в чат, сохранить страницу в файл (`00-задание.md` или иной) в подпапку задания, либо
кратко пересказать содержание. Дальше действовать по обычному шагу 0 skill'а.

Логин через `curl`/HTTP по логину-паролю из `.env` тоже не работает и не стоит пробовать:
форма входа на university.zerocoder.ru — JS-виджет GetCourse (поля email/password рендерятся
скриптом, в исходном HTML их нет), плюс на сайте антибот-защита (cookie `dd_bdfhyr`, похоже на
Datadome), которая блокирует скриптовые запросы. Без headless-браузера (Playwright/Puppeteer,
которого в этой среде нет) залогиниться не получится — не тратить время на реверс-инжиниринг
AJAX-эндпоинта логина, сразу просить пользователя открыть урок в своём браузере.

## Perr4.1 — при имитации кастомных формул Google Sheets-расширений через сырой API нужно явно прописывать их скрытое поведение
Формулы вроде `GPT_TRANSLATE(ячейка;"English")` или `GPT_EXTRACT(ячейка;"email")` в расширениях
для Google Sheets получают часть инструкции не текстом, а отдельным параметром формулы (язык
перевода, что извлекать). Если при генерации эталонных примеров такой формулы напрямую слать
в Chat Completions API только содержимое ячейки (без этого параметра), модель не поймёт задачу:
`GPT_TRANSLATE` вернул текст на языке оригинала вместо перевода, `GPT_EXTRACT(...; "email")`
вернул письмо целиком вместо самого email. Заметил только после ручной сверки сгенерированных
результатов (не поверил на слово, что раз запрос прошёл без ошибки — значит результат верный).

Как применять: при генерации примеров/эталонов для формул с параметрами вне текста промпта
(перевод, извлечение, любая формула, где часть поведения задаётся не в самой ячейке) — всегда
явно добавлять это поведение в текст запроса к API (например: «переведи на английский, выведи
только перевод» или «извлеки только email, без лишних слов»), и после генерации выборочно
открыть результат и проверить на здравый смысл, а не полагаться на отсутствие ошибки API.

## Perr4.4 — кириллица в `curl -d '...'` через Bash-инструмент на Windows превращается в "?"
При тестировании локального API (`curl -X POST ... -d '{"message":"текст на русском"}'`) через
Bash-инструмент на Windows кириллические символы в аргументе командной строки молча заменяются
на литеральные "?" ещё до отправки запроса (несовпадение кодировки консоли/codepage). Сервер
получает уже испорченный текст — не ошибку, а валидный JSON с "????" вместо слов. ИИ-модель на
том конце, получив бессвязный ввод, не падает с ошибкой, а правдоподобно "додумывает" ответ
(например, обращается к собеседнику по случайному имени, которого тот не называл) — это выглядит
как баг в коде диалоговой логики, хотя код полностью исправен (проверено прямым вызовом функции
на Python с тем же текстом — сработало верно).

Как применять: для тестирования HTTP API с кириллицей (или любым не-ASCII текстом) на Windows —
никогда не передавать текст напрямую в `curl -d` через Bash-инструмент. Вместо этого писать
короткий Python-скрипт, который формирует JSON через `json.dumps(...).encode("utf-8")` и
отправляет его как байты (`urllib.request` или `requests`), либо явно прописывать
`PYTHONIOENCODING=utf-8` при печати результатов. Если бот/ассистент вдруг "не помнит" или путает
данные, которые пользователь только что назвал в тесте — первым делом проверить, не испортилась
ли кодировка на пути тестового запроса, а не сразу чинить логику диалога.

## Perr6.5 — расширения файлов в исходных материалах задания могут не соответствовать реальному формату
В папке с документами `Ювелир` два файла с расширением `.pdf` на деле оказались DOCX
(ZIP-контейнер с `word/document.xml` внутри — экспорт из Word сохранили с чужим
расширением), один файл с расширением `.docx` на деле был обычным PDF (`%PDF-1.5` в начале),
а другой `.docx` — простым текстовым файлом в UTF-8. Загрузчик, который выбирает парсер по
`Path.suffix`, либо падает с ошибкой парсинга (`PdfStreamError`, `PackageNotFoundError`),
либо тихо получает мусор.

Как применять: при загрузке пользовательских/учебных документов не доверять расширению
файла — определять реальный формат по первым байтам (`%PDF` → PDF, `PK\x03\x04` → ZIP-based
формат типа DOCX/XLSX/PPTX, иначе — считать простым текстом) и на основе этого выбирать
парсер. Особенно важно для материалов курса — там файлы часто редактировались/пересохранялись
вручную и расширение могло "отвалиться" от реального содержимого.

## Perr6.5 — библиотека faiss (C++) не открывает файлы по пути с кириллицей на Windows
`FAISS.save_local()`/`load_local()` из `langchain_community` внутри вызывают
`faiss.write_index()`/`faiss.read_index()` — функции C++-библиотеки faiss, которые открывают
файл через узкую (не Unicode/wide-char) строку. Если путь к проекту содержит не-ASCII символы
(в этом репозитории — кириллица, например `C:\Проекты\...`), эти функции падают с
`RuntimeError: ... could not open ... for writing: No such file or directory`, даже когда
целевая папка реально существует и Python нормально видит путь (в отличие от чистого
Python-кода вроде `pickle.dump`/`open()`, который на Windows использует wide-char API и с
такими путями работает без проблем). ChromaDB (через sqlite3 в Python) с тем же путём
проблем не создала.

Как применять: если в пути к проекту есть не-ASCII символы (кириллица и т.п.) и
используется `langchain`/сырой `faiss-cpu` для сохранения индекса на диск — не полагаться
на `save_local`/`load_local`. Вместо этого сериализовать индекс в память
(`faiss.serialize_index(store.index)` → `bytes`) и писать/читать эти байты обычным
Python `open()`/`Path.write_bytes()`/`Path.read_bytes()`, а `docstore` и
`index_to_docstore_id` сохранять через `pickle` тем же способом — вручную пересобирая объект
`FAISS(embedding_function=..., index=..., docstore=..., index_to_docstore_id=...)` при
загрузке. Общее правило: если C-расширение падает на "не такой" ошибке (файл/директория не
найдены, хотя точно существуют) на Windows — первым делом проверить, нет ли в пути не-ASCII
символов, прежде чем чинить логику создания папок.

## Perr6.5 — маленькая локальная модель (Ollama, llama3.2:3b) может зациклиться в бесконечный повтор без repeat_penalty/num_predict
При прогоне тестовых вопросов через `ChatOllama(model="llama3.2:3b", temperature=0.2)` без
явного `num_predict`/`repeat_penalty` один из ответов (открытый вопрос "какие материалы
используются в ювелирном деле?") выродился в повтор одного и того же списка слов
("...молибден, олово, свинец, цинк, марганец, хром, титан..." сотни раз подряд) и генерация
заняла почти 5 минут вместо обычных 15-30 секунд — модель застряла в петле повторения токенов.
Другие 7 из 8 тестовых вызовов на тех же настройках отработали нормально — проблема
воспроизводится не всегда, чаще на открытых/обобщающих вопросах, где модели "нечего
остановить".

Как применять: для маленьких локальных моделей (3B и меньше) через Ollama всегда явно
задавать `num_predict` (жёсткий потолок длины ответа, страховка от зависания) и
`repeat_penalty` (обычно 1.1–1.3) в конструкторе `ChatOllama`/аналоге — не полагаться на
дефолты библиотеки. Само по себе успешное завершение запроса без ошибки не значит, что ответ
осмысленный — при тестировании RAG/чат-пайплайна на локальных моделях обязательно вручную
читать сгенерированный текст целиком (или хотя бы его длину/наличие явных повторов), а не
только факт отсутствия исключения.

## Perr6.5 — дублирующиеся документы в базе RAG вытесняют релевантный фрагмент из top-K
Пользователь спросил у RAG-бота «как ухаживать за изделиями из янтаря?» и получил «информация
не найдена», хотя нужный абзац (с явным упоминанием «янтарь» 19 раз) в базе точно был —
проверено прямым поиском по тексту документов. Причина оказалась не в загрузке документов и
не в генерации ответа (модель честно отвечала на основе того, что ей передали), а в
векторном поиске: два файла в исходных материалах на 100% дублировали один и тот же общий
текст про уход за украшениями (плюс тот же текст частично повторялся в третьем, более крупном
файле). При `TOP_K = 4` три из четырёх выданных фрагментов оказывались копиями одного и того
же общего текста — единственный фрагмент с прямым ответом про янтарь был лишь на 16-м месте
среди 30 результатов поиска и не попадал в контекст модели.

Как применять: при подготовке документов для RAG на небольшом корпусе (десятки/сотни
чанков) — до индексации проверять данные на дублирующиеся или почти дублирующиеся файлы
(побайтовое сравнение текста между документами, не только по имени файла) и убирать
целиком повторяющиеся; при отладке «бот не нашёл то, что точно есть в базе» — первым делом
не полагаться на то, что "модель не разобралась", а измерить сам поиск напрямую
(`similarity_search_with_score` с большим `k`, например 20-30) и посмотреть, на каком месте
на самом деле оказался нужный фрагмент — если он далеко за пределами `TOP_K`, дело в
retrieval, а не в LLM.

## Perr6.5 — `Chroma.from_documents(..., persist_directory=...)` дописывает в старую коллекцию, а не заменяет её
При пересборке ChromaDB-индекса после изменения набора исходных файлов (переименование,
удаление дублей) количество фрагментов в базе не уменьшилось, а выросло — с ожидаемых ~100
до 350. Внутри коллекции обнаружились фрагменты уже удалённых/переименованных файлов
(`памятка_2....pdf`, `носка.docx`) наравне со свежими. `Chroma.from_documents()` при указанном
`persist_directory` каждый раз **добавляет** переданные документы к тому, что уже лежит на
диске в этой коллекции, а не пересоздаёт её с нуля — в отличие от `FAISS.from_documents()`,
который в этом проекте при каждой пересборке полностью перезаписывал файл индекса. Это тихо
накапливающийся баг: после каждой правки данных и повторной сборки поиск в ChromaDB
становится немного хуже (больше шума, больше устаревших фрагментов), без явной ошибки.

Как применять: перед пересборкой персистентной коллекции ChromaDB (`Chroma.from_documents`
с `persist_directory`) всегда удалять старую папку коллекции с диска (`shutil.rmtree` перед
`from_documents`), если цель — построить индекс заново с нуля, а не дополнить существующий.
При отладке "почему ChromaDB и FAISS находят разное" на одних и тех же данных — в первую
очередь сравнить фактическое количество документов в обеих базах (`store.get()` для Chroma /
размер `index_to_docstore_id` для FAISS) с ожидаемым числом чанков, а не сразу подозревать
разницу в алгоритмах поиска.

## Perr4.4 — не называть папку проекта `site/` в Python-проекте
Изначальный план предполагал `site/site_app.py` для сайт-версии ассистента (по аналогии с
`bot.py` для Telegram). `site` — имя модуля стандартной библиотеки Python (управляет
site-packages при старте интерпретатора). Папка с таким именем, добавленная в `sys.path` (а её
пришлось добавлять, чтобы `site_app.py` мог импортировать соседние `assistant.py`/`storage.py` из
родительской папки), могла бы затмить собой стандартный модуль `site` для последующих `import
site` в этом процессе.

Как применять: для сайт-версии/веб-части python-проекта использовать имя `website/` (или любое
другое, не совпадающее с модулями стандартной библиотеки), а не `site/` — заранее сверяться, что
имя папки/модуля не дублирует `os`, `site`, `types`, `token` и другие стандартные модули.

## Perr7.1 — перед тем как ставить новое ПО на сервер, спросить, нет ли уже готового
Задание требовало локальную транскрибацию речи без ChatGPT API на удалённом сервере с n8n.
Первый план — собрать whisper.cpp с нуля. Но на этом же сервере уже год работал другой проект

пользователь/порт), не трогая и не встраиваясь в чужой код.

## Perr7.1 — REST API n8n не поддерживает создание OAuth2-типа credential (googleSheetsOAuth2Api и подобные)
Попытка создать credential типа `googleSheetsOAuth2Api` через `POST /api/v1/credentials`
упирается в противоречивую схему: эндпоинт `GET /api/v1/credentials/schema/<type>` показывает
условные поля (`useDynamicClientRegistration`, `grantType`), от значения которых зависит, какие
ещё поля обязательны — но сами эти условные поля НЕ входят в список разрешённых свойств
(`additionalProperties: false`), то есть их нельзя ни передать, ни пропустить так, чтобы схема
прошла валидацию. Похоже на баг/недоделку в публичном API n8n именно для credential-типов на
основе generic OAuth2. Обычные типы (`imap`, `openAiApi` и подобные без условной логики)
создаются через API нормально.

Как применять: не тратить время на подбор полей для OAuth2-based credential (Google, и вероятно
другие похожие) через REST API n8n — сразу создавать такие credentials вручную через UI n8n
(логин/пароль обычно уже есть в `.env` проекта). Также саму авторизацию (клик "Connect my
account" с входом через Google) в любом случае должен сделать сам пользователь в браузере — её
нельзя пройти headless-скриптом, если у OAuth-клиента не настроен подходящий redirect URI
(бывает `redirect_uri_mismatch`, если клиент заведён не под адрес n8n) или сам OAuth consent
screen ещё в статусе "Testing" без добавленного в Test users аккаунта (тогда будет "Ошибка 403:
доступ запрещён" уже после исправления redirect_uri).

## Perr7.1 — Gmail блокирует вход по IMAP с обычным паролем аккаунта всегда, независимо от 2FA
Прямая проверка (`imaplib.IMAP4_SSL(...).login(...)`) с обычным паролем аккаунта из `.env`
стабильно падает с `AUTHENTICATIONFAILED`/`Application-specific password required` — это не
особенность конкретного аккаунта, а общая политика Google: базовая парольная аутентификация для
IMAP/SMTP отключена для всех аккаунтов, работает только специальный App Password. Чтобы его

## Perr7.1 — n8n в docker-контейнере не видит 127.0.0.1 хоста; узнать реальный адрес можно эмпирически через реальный HTTP-узел
Локальный сервис на хосте (`127.0.0.1:8098`) был недоступен из HTTP Request node в n8n
("connection refused"/"the server is offline"), хотя с самого хоста (по SSH) сервис отвечал
нормально. Прямой способ проверки (`docker inspect` контейнера n8n на предмет `NetworkMode`) не
сработал — у выделенного SSH-пользователя не было доступа к Docker (`permission denied` на
`/var/run/docker.sock`), а `Execute Command`-узел в n8n оказался отключён на этом инстансе
(вероятно, специально из соображений безопасности — и локальный классификатор безопасности тоже
блокирует связку "публичный webhook + выполнение команд" на чужом/общем сервере, так что даже
если бы узел работал, так тестировать не стоило). В сумме это означало: нет прямого способа
узнать сетевые настройки контейнера, надо было выяснять эмпирически.
Рабочий способ: временно подставить в реальный сценарий (через уже существующий, легитимный
триггер — email, не публичный webhook) `HTTP Request`-узел с несколькими URL-кандидатами
(`host.docker.internal`, `172.17.0.1`, `172.18.0.1`, ...) и по разнице ошибок понять, что
происходит: `getaddrinfo`/`incorrect host` = имя не резолвится вообще, `connection refused` =
сеть до хоста доходит, но никто не слушает именно на этом адресе. Это быстро подсказало решение:
не хост недостижим, а наш собственный сервис слушал только `127.0.0.1` — после того как
переключили его на `0.0.0.0`, шлюз docker-моста (`172.17.0.1`) заработал.

Как применять: если n8n (или другой оркестратор) задеплоен в контейнере, а локальный сервис,
который он должен вызывать, живёт на том же физическом хосте — не считать по умолчанию, что
`127.0.0.1` сработает, даже если с самого хоста всё выглядит нормально. Если нет доступа к
`docker inspect`/`docker network`, можно определить рабочий адрес эмпирически: подставить
несколько адресов-кандидатов в реальный (не публично уязвимый) HTTP-узел и по типу ошибки понять,
на каком этапе рвётся связь — резолвинг имени или уже сам порт. И почти всегда локальный сервис,
который должен быть виден извне контейнера, придётся явно перевести с `127.0.0.1` на `0.0.0.0` —
в этом случае стоит сразу добавить простую защиту токеном/заголовком, раз порт становится видимым
шире, чем предполагалось изначально.

## Perr7.1 — синхронный тяжёлый код в async-обработчике FastAPI блокирует весь сервис целиком, включая health-check
Эндпоинт `/transcribe` вызывал `model.transcribe()` (faster-whisper) и `subprocess.run(ffmpeg)`
напрямую внутри `async def`-обработчика. Оба вызова синхронные и CPU-тяжёлые — они блокируют
единственный поток asyncio event loop целиком. Пока шла обработка одного файла, сервис не отвечал
вообще ни на что, включая простой `GET /health` — это выглядело как "сервис упал", хотя процесс
был жив и просто занят. На одном из тестовых файлов обработка неожиданно растянулась на 14+ минут
(вероятно, беглый цикл/зацикливание модели на конкретном фрагменте — похожая история уже была с
Ollama в Perr6.5), и всё это время сервис был полностью недоступен, а клиент (n8n) в итоге обрывал
соединение по своему таймауту, оставляя сервер молотить впустую.

Как применять: любой блокирующий/CPU-тяжёлый вызов (транскрибация, генерация, вызов внешнего
бинаря через `subprocess.run`) внутри async-обработчика FastAPI/Starlette оборачивать в
`asyncio.to_thread(...)`, а сверху — в `asyncio.wait_for(..., timeout=N)` с разумным жёстким
потолком. Это не ускоряет саму обработку, но: (1) не даёт одному медленному запросу полностью
парализовать сервис (health-check и другие запросы продолжают отвечать), и (2) гарантирует, что
клиент получит понятную ошибку по таймауту вместо вечного зависания. Отдельно стоит подстраховаться
от зацикливания декодера на маленьких CPU-моделях: простой `beam_size=1` без сложных доп. фильтров
(`vad_filter` и т.п.) обычно стабильнее, чем настройки по умолчанию.

## Perr7.1 — IMAP-триггер n8n может объединить несколько новых писем в одно выполнение, и один упавший item валит все остальные

items по общему графу узлов. Если на каком-то узле без `continueOnFail` падает хотя бы один item
(например, конкретный файл слишком долго обрабатывается и превышает таймаут), падает **всё**
выполнение — ни один item, включая те, что уже успешно прошли до этого узла, не доходит до
записи в Google-таблицу. Внешне это выглядит как "все записи не обработались", хотя часть из них
по факту отработала нормально на предыдущих шагах.

Как применять: при отладке сценария, который принимает пачку писем/файлов, не считать, что "одно
письмо = одно выполнение" — реальное количество items в конкретном выполнении нужно смотреть в
самих данных (`runData` триггера), а не только по числу writes в источнике. Для чистой диагностики,
какой именно item/файл вызывает проблему, надёжнее прогонять их по одному с паузами (дождаться
завершения предыдущего перед отправкой следующего), а не пачкой. Для продакшна стоит явно решить:
либо разносить приём по времени, либо включать `continueOnFail`/`onError: continueRegularOutput`
на узлах, где сбой одного item не должен ронять всю пачку.

документ эту причину не называет, он лишь фиксирует факт. Заметил только при целенаправленной
повторной сверке черновика с оригиналом перед коммитом, а не по ошибке компиляции или тесту —
такое не ловится автоматически.

Как применять: когда результат задания — не работающий код, а **текст, объясняющий существующую
систему** (архитектурный разбор, демо-документ, sales-питч про свою же платформу), риск
"дописать логичное, но не подтверждённое источником объяснение" выше, чем в коде, потому что
текст не падает с ошибкой, если факт неверен. Для каждого конкретного технического утверждения в
таком документе (номер строки, точное поведение, причина бага, точный формат вывода) — перед
финальным коммитом отдельно свериться с первоисточником (реальный файл кода/строка, а не только
архитектурный `.md`-пересказ) и убрать любую формулировку, которая заполняет пробел в источнике
"на правдоподобии", а не на факте. Если причина явления в источнике не указана — так и написать
("случилось X", без "потому что Y"), а не придумывать правдоподобное Y.

## Perr9.1 — у reasoning-моделей OpenAI лимит `max_completion_tokens` съедают скрытые рассуждения
Экзаменатору (`gpt-5`, `reasoning_effort="low"`) был выставлен `max_completion_tokens=800`, чтобы
короткий JSON с оценкой не стоил дорого. На двух из шести вызовов модель потратила все 800 токенов
на внутренние рассуждения (`reasoning_tokens=800`) и вернула пустую строку — без ошибки API, просто
`content=""`. В таблице это выглядело как «оценка NaN», а средняя оценка по режиму тихо считалась
по оставшимся строкам.

Как применять: для `gpt-5`-семейства (и любых reasoning-моделей) лимит вывода задавать с большим
запасом (2–4 тыс. токенов даже для однословного ответа) или не задавать вовсе; в разборе ответа
отдельно проверять случай «`tokens_out == лимит` и пустой текст» и считать его обрывом, а не
ответом. Стоимость считать по `completion_tokens` целиком — он уже включает `reasoning_tokens`.

## Perr9.1 — самая маленькая локальная модель как классификатор может «схлопнуться» в один класс
По логике урока дежурный должен быть самой дешёвой моделью. Проверка на 24 размеченных вопросах:
`gemma4:e2b` (2 млрд) отвечает за 5 с, но даёт 58 % точности — почти всё называет «medium»,
включая 7 из 8 сложных вопросов. `gemma4:12b` — 18 с и 96 % (одна ошибка, причём в «безопасную»
сторону medium→hard). На трёх вопросах smoke-теста обе выглядели бы прилично.

Как применять: перед тем как ставить маленькую модель на маршрутизацию, прогнать её на всём
размеченном наборе (это бесплатно для локальных моделей) и смотреть матрицу ошибок, а не только
общую точность: ошибка «сложный → простой» дороже ошибки «простой → сложный», потому что первая
портит качество, а вторая только цену. Скрипт сравнения стоит оставить в папке задания —
это готовый «скриншот» для отчёта.

## Perr9.1 — на CPU время локальной классификации определяется длиной системного промпта
Один и тот же вопрос `gemma4:12b` на CPU классифицировал за ~5 с с коротким системным промптом
(одна строка) и за ~18 с с полным (≈200 токенов с описанием трёх уровней): генерация — всего
2 токена, всё время уходит на обработку промпта (≈12 токенов/с). Кэш префикса Ollama здесь не
помог. Это заметно меняет сравнение «время А против Б»: дежурный добавляет к каждому вопросу
столько же секунд, сколько облачная модель тратит на весь ответ.

Как применять: при замерах latency локальных моделей на CPU считать системный промпт частью
стоимости и держать промпт классификатора максимально коротким; у Gemma 4 обязательно
`"think": false`, иначе режим рассуждений на CPU добавляет минуты. В отчёте честно
показывать время дежурного отдельной полосой, а не прятать его внутри ответа.

## Perr9.1 — в новых pandas `groupby(...).apply(f)` не передаёт в `f` столбец группировки
`df.groupby("ожидали").apply(lambda g: (g["ожидали"] == g["получили"]).mean())` упал с
`KeyError: 'ожидали'` — с pandas 2.x/3.x группирующий столбец исключается из передаваемого
подкадра. Ошибка всплыла только на smoke-прогоне после трёх минут реальных вызовов моделей.

Как применять: считать долю совпадений через булеву маску без `apply`
(`(df[df.a == t].b == t).mean()` по каждому классу) — короче и не зависит от версии pandas;
smoke-прогон всегда делать до полного, чтобы такие ошибки стоили минуты, а не часа.

## Perr9.2 — имя модели не говорит, сколько памяти она займёт (Gemma 4 «E2B» = 5,1 млрд параметров)
При сборе данных для расчёта требований к железу выяснилось: `gemma4:e2b` в Ollama показывает
`parameter_size=5.1B` и весит 7,2 ГБ — при том что «E2B» читается как «2 млрд». Буква E означает
*effective* (активных параметров при инференсе ~2 млрд, физически в файле 5,1 млрд — архитектура
MatFormer с послойным отбором). Расчёт «2 млрд × 0,5 байта (Q4) = 1,2 ГБ» ошибается в шесть раз.
Для сравнения, `gemma4:12b` при 11,9 млрд параметров в том же Q4_K_M весит 7,6 ГБ — почти столько же.

Как применять: для оценки памяти под модель брать фактический размер файла весов (`ollama list`,
карточка модели на Hugging Face, поле `parameter_size` в `/api/tags`), а не число из названия.
Названия моделей содержат маркетинговые и архитектурные сокращения (E2B/E4B, A3B у MoE-моделей),
где заявленное число относится к активным, а не ко всем параметрам.

## Perr9.1 — один зависший HTTP-запрос делает бессмысленной всю метрику времени
В эксперименте по сравнению схем вызова моделей замерялось время каждого ответа. Один запрос к
`gpt-5` на живой сети провисел **7609 секунд** (медиана по 34 таким же вызовам — 36 с) и в
одиночку дал 84 % суммарного времени режима: сравнение «быстрее/медленнее» превратилось в шум.
Клиент `openai` по умолчанию создаётся без явного таймаута, поэтому запрос просто ждал.
Ошибки при этом не было — в отчёте это выглядело бы как «мультимодельность в 9 раз медленнее».

Как применять: любой клиент внешнего API в эксперименте с замером времени создавать с явным
таймаутом (`OpenAI(timeout=300, max_retries=2)` и аналогично для других SDK). После прогона
всегда смотреть **распределение** времени (медиана и максимум), а не только сумму: выброс в
100 раз означает сетевой сбой, а не свойство модели. Ответы стоит кэшировать по ключу
(модель + промпт), тогда перезамер выброса стоит одного повторного вызова, а не всего прогона —
для этого в папке задания лежит `fix_outlier.py`.

## Perr9.2 — блокирующий вопрос надо задавать только про сам блокирующий шаг, а не про всю работу
Задание требовало два документа в Google Docs с доступом на чтение. Я задал вопрос
«создавать ли документы в вашем Google Диске и открывать ли доступ» — и остановил работу
**целиком** до ответа, хотя подтверждения требовал только последний шаг (публикация в чужом
аккаунте). Всё содержание — сбор данных, расчёты, оба текста — можно было писать сразу.
Пользователь вернулся с вопросом «9.2 готов?», когда не было сделано ничего, кроме концепции.
В итоге выяснилось, что Google Docs вообще не нужны: «можно оставить на GitHub, лектор прочитает».

Как применять: разделять задание на «что можно делать без разрешения» и «что нельзя»,
и блокировать только второе. Документ, код, расчёты в своей папке — всегда делаются сразу;
подтверждения требуют лишь действия наружу (запись в чужой аккаунт, публикация, рассылка,
покупка). Вопрос формулировать в конце готовой работы: «всё готово, осталось опубликовать —
подтвердите», а не «можно ли начинать».

## Perr9.2 — по замерам скорости генерации вычисляется пропускная способность памяти, и это проверяемо
Для оценки «какая видеокарта нужна» вместо цитирования чужих бенчмарков сработал расчёт из
физики: чтобы выдать один токен, модель обязана прочитать все активные веса, поэтому
*скорость генерации = пропускная способность памяти / объём активных весов*. Подстановка трёх
независимых замеров одной машины (две разные модели плюс прогретый запуск) дала одно и то же
число — 38 ГБ/с. Совпадение трёх точек подтверждает и формулу, и замеры, и позволяет
предсказать скорость на другой видеокарте по её паспортной пропускной способности.

Как применять: в любом задании про «оценку железа» искать соотношение, которое можно проверить
на нескольких имеющихся замерах, и показывать саму проверку — это сильнее, чем таблица
характеристик из интернета. Для моделей вида E2B/E4B/A3B в формулу идут **активные** параметры
(скорость), а в расчёт памяти — **все** (объём файла).

## Perr9.2 — Википедия ошибается в характеристиках железа, официальные datasheet нет
При сборе таблицы видеокарт Википедия дала RTX 3090 = 420 Вт (официально у NVIDIA 350 Вт) и
для A100 80 ГБ — пропускную способность 1555 ГБ/с, которая на самом деле относится к версии
на 40 ГБ (у 80 ГБ это 1935 ГБ/с для PCIe и 2039 для SXM). Обе ошибки нашлись только при сверке
с официальным datasheet. Если бы числа попали в документ, вывод «какую карту брать» изменился бы.

Как применять: характеристики железа брать из datasheet производителя (страница продукта или
PDF), Википедию использовать только для того, чего в datasheet нет (число ядер CUDA у серверных
карт там бывает полнее). PDF-datasheet, который WebFetch не разбирает, всё равно скачивается во
временный файл — его текст достаётся через `pypdf`, как в уроке Perr8.1.

## Perr10.2 — селектор по id перебивает утилитарный класс `.hidden`, и блок остаётся видимым
В веб-приложении блок «идёт генерация» был помечен классом `hidden` (`display: none`), но при
загрузке страницы всё равно показывался. Причина: ниже в таблице стилей стояло правило
`#status { display: flex }`, а селектор по идентификатору сильнее селектора по классу,
независимо от порядка строк в файле. Тесты этого не видели — они проверяют ответы сервера, а не
то, как выглядит страница. Дефект нашёлся на первом же скриншоте.

Как применять: утилитарные классы состояния (`.hidden`, `.disabled`) задавать с `!important` —
это тот редкий случай, когда он уместен, потому что класс обязан побеждать любое правило вёрстки.
И обязательно смотреть на готовую страницу глазами: «все тесты зелёные» ничего не говорит о том,
что видит пользователь.

## Perr10.2 — скриншот веб-страницы снимается одной командой через установленный Edge, без Playwright
Для заданий, где требуется «прислать скриншоты приложения», не нужен ни Playwright, ни ручное
нажатие PrintScreen. На машине уже есть Edge и Chrome, и оба умеют снимать страницу без окна:

    msedge --headless=new --disable-gpu --hide-scrollbars --window-size=1200,1000 \
           --screenshot="results\screenshots\01.png" "http://127.0.0.1:5055/"

Как применять: поднять приложение на нестандартном порту (чтобы не мешать рабочим сервисам),
снять два-три кадра ключевых экранов, положить в `results/screenshots/`. Скриншот получается
одинаковым при каждом повторе и не зависит от размера окна — его можно пересоздать командой,
а не искать в переписке. Для приложений, которым нужен платный ключ, стоит заранее предусмотреть
режим `--demo` с заглушками: тогда интерфейс снимается и проверяется бесплатно.

## Perr10.1/10.3 — задание на платный API делается целиком до момента оплаты
Три задания модуля 10 требуют платных ключей (Yandex Cloud, Proxy API), которых у пользователя
не оказалось. Ждать ключ, ничего не делая, было бы повторением ошибки задания 9.2. Вместо этого
написан и проверен весь код: 63 теста на подменённых клиентах покрывают сборку запроса, опрос
асинхронной операции, декодирование результата, обработку всех частых ошибок доступа и
безопасность имени файла. Остались только сами вызовы API.

Как применять: для задания с платным внешним сервисом сразу разделять работу на «логика» и
«деньги». Логику писать и тестировать на подменённом клиенте (передавать сетевые функции
параметрами — так их легко заменить), добавлять режимы `--dry-run` и `--demo`, а в отчёте прямо
писать, какой пункт задания закрыт и какой ждёт ключа, с пошаговой инструкцией получения.
Тогда после появления ключа остаётся один запуск, а не день работы.

## Perr10.1 — «нет доступа» от облачного API может означать, что API сменился, а не что не хватает прав
Генерация картинок через Yandex ART отвечала `403 Access to model art://yandex-art/latest denied`.
Сообщение прямо указывает на права, и час ушёл на проверку ролей, областей действия ключа и
биллинга — всё оказалось настроено верно: у сервисного аккаунта были `ai.imageGeneration.user` и
`ai.editor`, у ключа область `yc.ai.imageGeneration.execute`, счёт активен, а текстовые модели тем
же ключом работали. Настоящая причина: Yandex AI Studio перешёл на OpenAI-совместимый API
(`https://ai.api.cloud.yandex.net/v1`, каталог параметром `project`, синхронный вызов
`client.images.generate`), а модель `yandex-art` из урока заменена на `yandex-art-2.0`.

Как применять: если 403 не уходит после того, как все права проверены, не продолжать крутить
настройки. Открыть **каталог моделей в консоли сервиса** и сверить: существует ли модель с этим
именем и какой способ вызова указан на её странице. Быстрый признак смены API — соседние модели
того же сервиса работают тем же ключом. В материалах курса код устаревает быстрее текста: урок
2026 года уже ссылался на снятый эндпоинт.

## Perr10.1 — для логотипа короткий промпт работает лучше подробного
Первая серия промптов была на 250–300 символов с перечислением деталей (цвета, композиция,
материал, назначение) — YandexART выдал красивые, но декоративные иллюстрации, не знаки.
Сокращение до 120–135 символов по схеме «Логотип: <один объект>, <два цвета>. Плоский
минималистичный знак по центру на белом фоне. Без текста.» дало настоящие логотипы. Отдельно:
слово «галочка» модель рисовала треугольником, помогло уточнение «галочка как знак подтверждения
check mark».

Как применять: для генерации знака держать промпт коротким, называть один объект и не более двух
цветов, начинать со слова «Логотип» (без него модель уходит в иллюстрацию) и заканчивать запретом
надписей. Неоднозначный термин подкреплять английским эквивалентом. Обе серии стоит сохранять
рядом — сравнение «до и после» само по себе результат для отчёта по промпт-инжинирингу.
У модели есть предел длины промпта (у YandexART 2.0 — 500 символов), он указан в карточке модели.

## Perr10.2 — параллельные задачи ломают файл по схеме «прочитать целиком → дописать → записать целиком»
Веб-приложение сохраняло результаты в общий JSON-файл: каждая завершённая генерация читала файл,
вставляла запись и переписывала его целиком. Пока задачи шли по одной, всё работало. На трёх
одновременных генерациях записи наложились друг на друга, файл перестал разбираться, а обработчик
ошибки молча возвращал пустой список — галерея на странице просто оказалась пустой, без единого
сообщения об ошибке. Тесты этого не ловили: они запускали задачи последовательно.

Как применять: любое «прочитал файл → изменил → записал» из нескольких потоков защищать
блокировкой и писать через временный файл с последующей заменой. В `except json.JSONDecodeError`
никогда не возвращать пустоту молча — печатать сообщение, иначе потеря данных выглядит как
«ничего не сохранилось». В тесты добавлять прогон с десятком одновременных записей: он ловит
такую гонку за доли секунды.

## Perr10.3 — формат чужого API быстрее выяснить одним пробным запросом, чем чтением документации
Для генерации видео через RouterAI нужно было знать: адрес, поля запроса, форму ответа, как
опрашивать статус и как скачивать файл. Страница документации не отдавалась (редиректы и 404),
и попытки её достать тратили время. Один POST на `/api/v1/videos` ответил
`{"id", "polling_url", "status": "pending"}` — этого хватило, чтобы написать весь код; второй
запрос по `polling_url` показал формат готового ответа (`unsigned_urls`, `usage.cost`).

Как применять: если сервис уже доступен по ключу, начинать с одного дешёвого пробного запроса и
печатать ответ целиком, а не искать спецификацию. Заодно сразу видны настоящие имена статусов
(здесь `pending` → `completed`, а не `queued` → `complete`, как писал урок). Для платных операций
первый пробный запрос стоит делать самой дешёвой моделью и коротким параметром — он и станет
первым результатом, если получится.

## Perr10.3 — у посредников доступ к моделям и цена различаются в разы, это стоит измерить до прогона
Один и тот же четырёхсекундный ролик обошёлся в 43,8 кредита на `google/veo-3.1-fast` и
в 21,9 на `google/veo-3.1-lite` — вдвое дешевле при том же результате для задания. При остатке
в 109 кредитов это разница между «хватит на два ролика» и «на пять». Остаток счёта отдаётся
отдельным эндпоинтом (`/api/v1/credits`), и его полезно показывать прямо в команде проверки.

Как применять: в заданиях с платной генерацией добавлять команду `--check`, которая показывает
остаток и пересчитывает его в число оставшихся запусков, а в отчёт выносить таблицу «модель —
цена — время». Пробный прогон делать дешёвой моделью: для скриншота прогресс-бара и проверки
пайплайна качество флагмана не нужно.

## Perr10.3 — прогресс-бар не попадает в лог: возврат каретки складывает его в одну строку
Задание требовало скриншот терминала с прогресс-баром. Вывод был сохранён через `tee`, но в
файле все шаги прогресса склеились в одну длинную строку: полоса перерисовывает себя символом
`\r`, а не переводом строки. На картинке из такого лога виден только последний кадр.

Как применять: перед отрисовкой лога в картинку разворачивать перерисовку обратно — бить строку
по `\r` и делать каждый шаг отдельной строкой. Тогда на скриншоте виден весь ход работы:
очередь, обработка, готово. Это честный вывод программы, просто развёрнутый по шагам.

## Perr10.4 — состояние служб с сервера лучше брать выводом команд, а не скриншотом
Задание требовало скриншот `screen -ls`. Вместо кадра был снят живой вывод `systemctl --user
status`, `list-units` и `journalctl` и сохранён текстом в папку задания. Это оказалось сильнее
скриншота: в тексте видны время непрерывной работы (четверо суток), автозапуск при загрузке,
номера процессов, занятые порты и — главное — строки журнала с таймингами каждой стадии
(распознавание 4,0 с, модель 2,9 с, синтез речи 1,5 с, итого 8,7 с). Такие цифры становятся
доказательством «прогресса со статусами», которое картинка дать не может. Попутно в выводе
обнаружилось, что веб-служба заняла 6,7 ГБ при мягком пределе 7,3 ГБ — то самое состояние,
которое в документации проекта описано как причина прошлой аварии.

Как применять: там, где задание просит скриншот состояния сервера, снимать вывод команд в файл
и коммитить его рядом с отчётом. Текст можно процитировать в отчёте построчно, он ищется
поиском и не теряет читаемость при сжатии. Скриншот оставлять для того, что в терминал не
выводится: интерфейс, переписка, диалог браузера.

## Perr10.4 — пара скриншотов «до и после» доказывает требование, которое одним кадром не покажешь
Задание требовало, чтобы Telegram-бот обновлял одно сообщение, а не слал новые. Одним кадром
это недоказуемо: на готовом ответе не видно, был ли он новым сообщением. Доказательством стала
пара кадров: на первом виден вопрос с отметкой времени и сообщение-заглушка «Thinking», на
втором — тот же вопрос с той же отметкой, а на месте заглушки ответ, и новых сообщений в ленте
не прибавилось.

Как применять: когда требование касается *изменения состояния* (заменилось, а не добавилось;
обновилось, а не перерисовалось), просить у пользователя именно пару кадров и в отчёте явно
называть, что их сравнивает: одинаковая отметка времени, исчезнувший элемент, неизменившийся
счётчик. Иначе проверяющий увидит два красивых скриншота и не поймёт, что именно доказано.

## Perr10.5 — узел импортировался без ошибок, но был не тем
В n8n два разных узла с похожим названием: старый `n8n-nodes-base.openAi` и современный
`@n8n/n8n-nodes-langchain.openAi`, где живёт операция «Message a Model». Цепочка со старым
узлом импортировалась, включилась и отработала без единой ошибки — только вместо поста на
заданную тему модель вернула обрывок рекламы интернет-магазина: этот узел по умолчанию
обращается к устаревшему endpoint завершения текста и игнорирует и системную роль, и промпт.

Как применять: успешный импорт и зелёный статус выполнения не подтверждают, что узел выбран
верно. Первый запуск проверять по *содержанию* ответа, а не по статусу. Если в задании
указано название операции («Message a Model»), искать узел по этому названию в установленном
n8n, а не по совпадению слова в типе узла.

## Perr10.5 — версии узлов сверять до развёртывания, внутри контейнера
Список версий, которые понимает установленный n8n, лежит прямо в образе: 
`grep -o "version: \[[^]]*\]" .../<Узел>.node.js`. Проверка заняла минуту и нашла
собственную ошибку — в цепочке стояла версия, которой у выбранного типа узла не существует.
Заодно выяснилось, что у одного типа узла бывает две серии версий (1…1.8 и 2…2.3), и брать
надо младшую из подходящих, если цепочку предстоит открывать и на более старых n8n.

Как применять: перед развёртыванием workflow на незнакомой версии n8n вытащить список
поддерживаемых версий из контейнера и закрепить его тестом, который сверяет `typeVersion`
каждого узла в `workflow.json`. Тест ловит ошибку на ноутбуке, а не на живом сервере.

## Perr10.5 — журнал выполнения n8n не читается обычным json.loads
Поле `data` в ответе `/rest/executions/<id>` — это формат flatted: плоский массив, где
вместо вложенных объектов стоят номера элементов. Без распаковки не видно ни что отдал
каждый узел, ни на каком узле цепочка упала. Распаковка — около двадцати строк рекурсии
(см. `Perr10.5/last_run.py`).

Как применять: когда нужно понять, почему цепочка вернула «Error in workflow», не гадать по
ответу вебхука — распаковать журнал и посмотреть по узлам. Ответ вебхука показывает только
факт падения, а причина видна лишь в журнале.

## Perr10.5 — идентификатор Telegram-канала требует приставки -100
Числовой идентификатор канала, записанный без `-100` (например `3863639639` вместо
`-1003863639639`), Telegram API встречает ответом «chat not found» — и это выглядит как
отсутствие прав у бота, хотя бот администратор. Проверяется за секунду:
`getChat?chat_id=...` и `getChatMember?chat_id=...&user_id=<id бота>`.

Как применять: перед сборкой цепочки публикации проверить канал и права бота двумя запросами
к Telegram API. Это дешевле, чем разбирать падение узла публикации в конце цепочки, когда
текст уже сгенерирован и деньги за него списаны.

## Perr10.6 — готовый узел собирает запрос под конкретный список моделей
Штатный узел OpenAI в n8n на операции «Generate an image» отвечал «Bad request» для модели
`gpt-image-1-mini`. В коде узла нашлась причина: он добавляет в тело `response_format` для
любой модели, **кроме** ровно `gpt-image-1`, а модели серии gpt-image такого поля не принимают.
Настройками это не обойти — поведение зашито.

Как применять: если в выпадающем списке узла нет нужной модели, это не косметика — узел
собирает запрос под те модели, что в списке. Проверять так: найти файл операции в контейнере
(`.../actions/<операция>.operation.js`) и прочитать, из чего складывается body. Обходной путь —
обычный HTTP-узел с предустановленным типом учётных данных: полный контроль над телом, а ключ
по-прежнему берётся из хранилища n8n и не попадает в файл цепочки.

## Perr10.6 — время ответа на отказ показывает, где стоит проверка
Защищённый вебхук n8n отвечает 403 за 0,2 секунды, тогда как успешный запрос идёт 16 секунд.
Эта разница — само по себе доказательство, что проверка стоит до запуска цепочки, и чужой
запрос не тратит ни токенов, ни денег на картинку. Если бы проверка была внутри цепочки,
отказ приходил бы примерно за то же время, что и успех.

Как применять: в отчёте о защите приводить не только код ответа, но и время. Пара «403 за
0,2 с против 200 за 16 с» объясняет проверяющему устройство защиты без единой схемы.

## Perr10.6 — подмена модулей в одном тесте ломает другой
Новый тестовый файл падал только в паре с существующим: тот подменяет модули в `sys.modules`
заглушками, а pytest импортирует все файлы тестов до запуска любого. Вдобавок импорт подмодуля
привязывает его атрибутом к пакету, и `from package import module` читает именно атрибут, а не
`sys.modules` — восстанавливать нужно оба места.

Как применять: не импортировать «настоящий» модуль на уровне файла, если соседний тест его
подменяет. Загружать внутри теста и возвращать на место в cleanup — и проверять оба порядка
запуска, не только тот, в котором всё сошлось с первого раза.

## Perr10.7 — стоп-слова важнее выбора модели
Эталонная реализация из урока считала совпадение навыков по всем словам длиннее четырёх
букв. В русском тексте это значит, что «требования», «обязанности» и «который» из вакансии
засчитываются как совпавшие навыки, и любое резюме получает приличный процент. После
добавления стоп-слов профильное резюме набрало 53 балла по формуле, а резюме из чужой
области — 11. Смена модели такого разрыва не дала бы.

Как применять: там, где сравнение текстов идёт по пересечению слов, первым делом выбросить
служебную лексику и склеить синонимы — и только потом обсуждать модель. Проверять на двух
крайних примерах: заведомо подходящем и заведомо чужом. Если разрыв между ними меньше
двадцати баллов, дело не в модели.

## Perr10.7 — повторный прогон показывает, зачем нужна детерминированная часть
Два одинаковых прогона одного резюме дали у модели 95 и 90 баллов, а формула оба раза
выдала ровно 53. Это лучший аргумент в пользу смешанной оценки: решение о человеке должно
быть воспроизводимым, а объяснимую часть можно показать кандидату.

Как применять: в заданиях, где модель что-то оценивает в баллах, прогонять один и тот же
вход дважды и приводить обе цифры в отчёте. Это честнее, чем показывать один удачный
прогон, и сразу объясняет, зачем рядом стоит формула.

## Perr10.7 — порядок чистки PDF фиксировать тестом
В выгрузке из PDF слова разорваны переносом по слогам, а пустая строка означает конец
абзаца. Если сначала склеивать строки, а потом дефисы — дефис остаётся посреди слова.
Если склеивать наивно — вместе с переносами исчезают и границы абзацев. Обе ошибки
незаметны на глаз в готовом тексте, но портят разбор.

Как применять: чистку выгрузки из PDF собирать по шагам и каждый шаг закрывать отдельным
тестом на коротком примере (перенос по слогам, перенос внутри абзаца, пустая строка,
маркированный список). Абзацы прятать под метку до склейки строк и возвращать после.
