# Уроки из прошлых заданий

Сюда добавляются короткие заметки после каждого задания: что пошло не так и как это исправить в будущем, либо какой приём хорошо сработал. Формат записи:

```
## <номер-задания> — <короткий заголовок урока>
Что случилось / что сработало.
Как применять в следующий раз.
```

## Perr3.5 — httpx/telegram логируют токен бота в открытом виде
При стандартном `logging.basicConfig(level=INFO)` библиотеки `httpx` и `python-telegram-bot`
пишут в лог полный URL HTTP-запроса, а URL Telegram Bot API включает сам токен бота
(`https://api.telegram.org/bot<TOKEN>/...`). Токен утекает в лог-файлы в открытом виде,
даже если нигде в коде явно не печатается.

Как применять: в любом Telegram-боте на `python-telegram-bot`/`httpx` сразу после
`logging.basicConfig(...)` поднимать уровень логов до WARNING для логгеров `httpx` и
`telegram` (`logging.getLogger("httpx").setLevel(logging.WARNING)` и аналогично для
`telegram`), чтобы токен не оседал в логах/файлах.

## Perr3.5 — отправка голосового/аудио ответа в Telegram иногда обрывается по тайм-ауту
При реальном тесте на живой сети (не в лаборатории) `reply_audio()` изредка падал с
`telegram.error.TimedOut`/`httpx.ReadTimeout`, хотя вся дорогая часть (запросы к OpenAI,
генерация аудио) уже успешно завершилась — терялся только последний шаг доставки.
Обидно терять уже готовый результат из-за сетевого дребезга на "последней миле".

Как применять: для любой отправки крупного файла (аудио/видео/документ) пользователю
в конце пайплайна — оборачивать именно этот вызов в одну повторную попытку (try/except
с retry), а не весь пайплайн целиком; если не получилось даже со второй попытки —
пользователю должно прийти хотя бы текстовое уведомление, что результат готов, но
не доставлен полностью, а не полная тишина.

## Общее — ссылки на university.zerocoder.ru требуют авторизации, WebFetch их не видит
Страницы уроков на `university.zerocoder.ru/pl/teach/control/lesson/view?id=...` закрыты
логином (платформа GetCourse). WebFetch без авторизации получает только страницу входа,
а не содержимое урока — попытка "перейти по ссылке и изучить материал" напрямую не сработает.

Как применять: при получении ссылки на урок/задание zerocoder сразу (без пробной попытки
WebFetch) просить пользователя предоставить текст урока и домашнего задания — вставить
текст в чат, сохранить страницу в файл (`00-задание.md` или иной) в подпапку задания, либо
кратко пересказать содержание. Дальше действовать по обычному шагу 0 skill'а.

Логин через `curl`/HTTP по логину-паролю из `.env` тоже не работает и не стоит пробовать:
форма входа на university.zerocoder.ru — JS-виджет GetCourse (поля email/password рендерятся
скриптом, в исходном HTML их нет), плюс на сайте антибот-защита (cookie `dd_bdfhyr`, похоже на
Datadome), которая блокирует скриптовые запросы. Без headless-браузера (Playwright/Puppeteer,
которого в этой среде нет) залогиниться не получится — не тратить время на реверс-инжиниринг
AJAX-эндпоинта логина, сразу просить пользователя открыть урок в своём браузере.

## Perr4.1 — при имитации кастомных формул Google Sheets-расширений через сырой API нужно явно прописывать их скрытое поведение
Формулы вроде `GPT_TRANSLATE(ячейка;"English")` или `GPT_EXTRACT(ячейка;"email")` в расширениях
для Google Sheets получают часть инструкции не текстом, а отдельным параметром формулы (язык
перевода, что извлекать). Если при генерации эталонных примеров такой формулы напрямую слать
в Chat Completions API только содержимое ячейки (без этого параметра), модель не поймёт задачу:
`GPT_TRANSLATE` вернул текст на языке оригинала вместо перевода, `GPT_EXTRACT(...; "email")`
вернул письмо целиком вместо самого email. Заметил только после ручной сверки сгенерированных
результатов (не поверил на слово, что раз запрос прошёл без ошибки — значит результат верный).

Как применять: при генерации примеров/эталонов для формул с параметрами вне текста промпта
(перевод, извлечение, любая формула, где часть поведения задаётся не в самой ячейке) — всегда
явно добавлять это поведение в текст запроса к API (например: «переведи на английский, выведи
только перевод» или «извлеки только email, без лишних слов»), и после генерации выборочно
открыть результат и проверить на здравый смысл, а не полагаться на отсутствие ошибки API.

## Perr4.4 — кириллица в `curl -d '...'` через Bash-инструмент на Windows превращается в "?"
При тестировании локального API (`curl -X POST ... -d '{"message":"текст на русском"}'`) через
Bash-инструмент на Windows кириллические символы в аргументе командной строки молча заменяются
на литеральные "?" ещё до отправки запроса (несовпадение кодировки консоли/codepage). Сервер
получает уже испорченный текст — не ошибку, а валидный JSON с "????" вместо слов. ИИ-модель на
том конце, получив бессвязный ввод, не падает с ошибкой, а правдоподобно "додумывает" ответ
(например, обращается к собеседнику по случайному имени, которого тот не называл) — это выглядит
как баг в коде диалоговой логики, хотя код полностью исправен (проверено прямым вызовом функции
на Python с тем же текстом — сработало верно).

Как применять: для тестирования HTTP API с кириллицей (или любым не-ASCII текстом) на Windows —
никогда не передавать текст напрямую в `curl -d` через Bash-инструмент. Вместо этого писать
короткий Python-скрипт, который формирует JSON через `json.dumps(...).encode("utf-8")` и
отправляет его как байты (`urllib.request` или `requests`), либо явно прописывать
`PYTHONIOENCODING=utf-8` при печати результатов. Если бот/ассистент вдруг "не помнит" или путает
данные, которые пользователь только что назвал в тесте — первым делом проверить, не испортилась
ли кодировка на пути тестового запроса, а не сразу чинить логику диалога.

## Perr6.5 — расширения файлов в исходных материалах задания могут не соответствовать реальному формату
В папке с документами `Ювелир` два файла с расширением `.pdf` на деле оказались DOCX
(ZIP-контейнер с `word/document.xml` внутри — экспорт из Word сохранили с чужим
расширением), один файл с расширением `.docx` на деле был обычным PDF (`%PDF-1.5` в начале),
а другой `.docx` — простым текстовым файлом в UTF-8. Загрузчик, который выбирает парсер по
`Path.suffix`, либо падает с ошибкой парсинга (`PdfStreamError`, `PackageNotFoundError`),
либо тихо получает мусор.

Как применять: при загрузке пользовательских/учебных документов не доверять расширению
файла — определять реальный формат по первым байтам (`%PDF` → PDF, `PK\x03\x04` → ZIP-based
формат типа DOCX/XLSX/PPTX, иначе — считать простым текстом) и на основе этого выбирать
парсер. Особенно важно для материалов курса — там файлы часто редактировались/пересохранялись
вручную и расширение могло "отвалиться" от реального содержимого.

## Perr6.5 — библиотека faiss (C++) не открывает файлы по пути с кириллицей на Windows
`FAISS.save_local()`/`load_local()` из `langchain_community` внутри вызывают
`faiss.write_index()`/`faiss.read_index()` — функции C++-библиотеки faiss, которые открывают
файл через узкую (не Unicode/wide-char) строку. Если путь к проекту содержит не-ASCII символы
(в этом репозитории — кириллица, например `C:\Проекты\...`), эти функции падают с
`RuntimeError: ... could not open ... for writing: No such file or directory`, даже когда
целевая папка реально существует и Python нормально видит путь (в отличие от чистого
Python-кода вроде `pickle.dump`/`open()`, который на Windows использует wide-char API и с
такими путями работает без проблем). ChromaDB (через sqlite3 в Python) с тем же путём
проблем не создала.

Как применять: если в пути к проекту есть не-ASCII символы (кириллица и т.п.) и
используется `langchain`/сырой `faiss-cpu` для сохранения индекса на диск — не полагаться
на `save_local`/`load_local`. Вместо этого сериализовать индекс в память
(`faiss.serialize_index(store.index)` → `bytes`) и писать/читать эти байты обычным
Python `open()`/`Path.write_bytes()`/`Path.read_bytes()`, а `docstore` и
`index_to_docstore_id` сохранять через `pickle` тем же способом — вручную пересобирая объект
`FAISS(embedding_function=..., index=..., docstore=..., index_to_docstore_id=...)` при
загрузке. Общее правило: если C-расширение падает на "не такой" ошибке (файл/директория не
найдены, хотя точно существуют) на Windows — первым делом проверить, нет ли в пути не-ASCII
символов, прежде чем чинить логику создания папок.

## Perr6.5 — маленькая локальная модель (Ollama, llama3.2:3b) может зациклиться в бесконечный повтор без repeat_penalty/num_predict
При прогоне тестовых вопросов через `ChatOllama(model="llama3.2:3b", temperature=0.2)` без
явного `num_predict`/`repeat_penalty` один из ответов (открытый вопрос "какие материалы
используются в ювелирном деле?") выродился в повтор одного и того же списка слов
("...молибден, олово, свинец, цинк, марганец, хром, титан..." сотни раз подряд) и генерация
заняла почти 5 минут вместо обычных 15-30 секунд — модель застряла в петле повторения токенов.
Другие 7 из 8 тестовых вызовов на тех же настройках отработали нормально — проблема
воспроизводится не всегда, чаще на открытых/обобщающих вопросах, где модели "нечего
остановить".

Как применять: для маленьких локальных моделей (3B и меньше) через Ollama всегда явно
задавать `num_predict` (жёсткий потолок длины ответа, страховка от зависания) и
`repeat_penalty` (обычно 1.1–1.3) в конструкторе `ChatOllama`/аналоге — не полагаться на
дефолты библиотеки. Само по себе успешное завершение запроса без ошибки не значит, что ответ
осмысленный — при тестировании RAG/чат-пайплайна на локальных моделях обязательно вручную
читать сгенерированный текст целиком (или хотя бы его длину/наличие явных повторов), а не
только факт отсутствия исключения.

## Perr6.5 — дублирующиеся документы в базе RAG вытесняют релевантный фрагмент из top-K
Пользователь спросил у RAG-бота «как ухаживать за изделиями из янтаря?» и получил «информация
не найдена», хотя нужный абзац (с явным упоминанием «янтарь» 19 раз) в базе точно был —
проверено прямым поиском по тексту документов. Причина оказалась не в загрузке документов и
не в генерации ответа (модель честно отвечала на основе того, что ей передали), а в
векторном поиске: два файла в исходных материалах на 100% дублировали один и тот же общий
текст про уход за украшениями (плюс тот же текст частично повторялся в третьем, более крупном
файле). При `TOP_K = 4` три из четырёх выданных фрагментов оказывались копиями одного и того
же общего текста — единственный фрагмент с прямым ответом про янтарь был лишь на 16-м месте
среди 30 результатов поиска и не попадал в контекст модели.

Как применять: при подготовке документов для RAG на небольшом корпусе (десятки/сотни
чанков) — до индексации проверять данные на дублирующиеся или почти дублирующиеся файлы
(побайтовое сравнение текста между документами, не только по имени файла) и убирать
целиком повторяющиеся; при отладке «бот не нашёл то, что точно есть в базе» — первым делом
не полагаться на то, что "модель не разобралась", а измерить сам поиск напрямую
(`similarity_search_with_score` с большим `k`, например 20-30) и посмотреть, на каком месте
на самом деле оказался нужный фрагмент — если он далеко за пределами `TOP_K`, дело в
retrieval, а не в LLM.

## Perr6.5 — `Chroma.from_documents(..., persist_directory=...)` дописывает в старую коллекцию, а не заменяет её
При пересборке ChromaDB-индекса после изменения набора исходных файлов (переименование,
удаление дублей) количество фрагментов в базе не уменьшилось, а выросло — с ожидаемых ~100
до 350. Внутри коллекции обнаружились фрагменты уже удалённых/переименованных файлов
(`памятка_2....pdf`, `носка.docx`) наравне со свежими. `Chroma.from_documents()` при указанном
`persist_directory` каждый раз **добавляет** переданные документы к тому, что уже лежит на
диске в этой коллекции, а не пересоздаёт её с нуля — в отличие от `FAISS.from_documents()`,
который в этом проекте при каждой пересборке полностью перезаписывал файл индекса. Это тихо
накапливающийся баг: после каждой правки данных и повторной сборки поиск в ChromaDB
становится немного хуже (больше шума, больше устаревших фрагментов), без явной ошибки.

Как применять: перед пересборкой персистентной коллекции ChromaDB (`Chroma.from_documents`
с `persist_directory`) всегда удалять старую папку коллекции с диска (`shutil.rmtree` перед
`from_documents`), если цель — построить индекс заново с нуля, а не дополнить существующий.
При отладке "почему ChromaDB и FAISS находят разное" на одних и тех же данных — в первую
очередь сравнить фактическое количество документов в обеих базах (`store.get()` для Chroma /
размер `index_to_docstore_id` для FAISS) с ожидаемым числом чанков, а не сразу подозревать
разницу в алгоритмах поиска.

## Perr4.4 — не называть папку проекта `site/` в Python-проекте
Изначальный план предполагал `site/site_app.py` для сайт-версии ассистента (по аналогии с
`bot.py` для Telegram). `site` — имя модуля стандартной библиотеки Python (управляет
site-packages при старте интерпретатора). Папка с таким именем, добавленная в `sys.path` (а её
пришлось добавлять, чтобы `site_app.py` мог импортировать соседние `assistant.py`/`storage.py` из
родительской папки), могла бы затмить собой стандартный модуль `site` для последующих `import
site` в этом процессе.

Как применять: для сайт-версии/веб-части python-проекта использовать имя `website/` (или любое
другое, не совпадающее с модулями стандартной библиотеки), а не `site/` — заранее сверяться, что
имя папки/модуля не дублирует `os`, `site`, `types`, `token` и другие стандартные модули.

## Perr7.1 — перед тем как ставить новое ПО на сервер, спросить, нет ли уже готового
Задание требовало локальную транскрибацию речи без ChatGPT API на удалённом сервере с n8n.
Первый план — собрать whisper.cpp с нуля. Но на этом же сервере уже год работал другой проект

Как применять: когда задание просит развернуть локальную модель/сервис на сервере, к которому

пользователь/порт), не трогая и не встраиваясь в чужой код.

## Perr7.1 — REST API n8n не поддерживает создание OAuth2-типа credential (googleSheetsOAuth2Api и подобные)
Попытка создать credential типа `googleSheetsOAuth2Api` через `POST /api/v1/credentials`
упирается в противоречивую схему: эндпоинт `GET /api/v1/credentials/schema/<type>` показывает
условные поля (`useDynamicClientRegistration`, `grantType`), от значения которых зависит, какие
ещё поля обязательны — но сами эти условные поля НЕ входят в список разрешённых свойств
(`additionalProperties: false`), то есть их нельзя ни передать, ни пропустить так, чтобы схема
прошла валидацию. Похоже на баг/недоделку в публичном API n8n именно для credential-типов на
основе generic OAuth2. Обычные типы (`imap`, `openAiApi` и подобные без условной логики)
создаются через API нормально.

Как применять: не тратить время на подбор полей для OAuth2-based credential (Google, и вероятно
другие похожие) через REST API n8n — сразу создавать такие credentials вручную через UI n8n
(логин/пароль обычно уже есть в `.env` проекта). Также саму авторизацию (клик "Connect my
account" с входом через Google) в любом случае должен сделать сам пользователь в браузере — её
нельзя пройти headless-скриптом, если у OAuth-клиента не настроен подходящий redirect URI
(бывает `redirect_uri_mismatch`, если клиент заведён не под адрес n8n) или сам OAuth consent
screen ещё в статусе "Testing" без добавленного в Test users аккаунта (тогда будет "Ошибка 403:
доступ запрещён" уже после исправления redirect_uri).

## Perr7.1 — Gmail блокирует вход по IMAP с обычным паролем аккаунта всегда, независимо от 2FA
Прямая проверка (`imaplib.IMAP4_SSL(...).login(...)`) с обычным паролем аккаунта из `.env`
стабильно падает с `AUTHENTICATIONFAILED`/`Application-specific password required` — это не
особенность конкретного аккаунта, а общая политика Google: базовая парольная аутентификация для
IMAP/SMTP отключена для всех аккаунтов, работает только специальный App Password. Чтобы его
создать, на аккаунте обязательно должна быть включена двухфакторная аутентификация — если её
нет, страница `myaccount.google.com/apppasswords` сразу показывает «Эта настройка недоступна для
вашего аккаунта» без объяснения причины.

Как применять: если задание требует принимать почту на Gmail через IMAP — сразу предупреждать
пользователя, что понадобится не обычный пароль, а App Password, и что для этого сначала нужно
включить 2FA. Если 2FA включать не хочется/страница App Passwords недоступна (например, включена
Расширенная защита) — быстрее завести отдельный свежий email специально под кейс, чем разбираться
с ограничениями старого аккаунта. При получении пароля от пользователя текстом — если он написан
"по буквам" вперемешку с обычными словами (например, кто-то надиктовал пароль и часть букв
превратилась в слово "times" из "t-i-m-e-s"), не гадать: попросить прислать пароль сплошной
строкой копипастом.

## Perr7.1 — n8n UI при пересохранении узла может тихо стирать параметры, совпадающие со значением по умолчанию
После того как пользователь открыл сценарий в UI n8n и сохранил его (просто чтобы привязать
credential к другому узлу), у соседнего узла `emailReadImap` (IMAP-триггер) из JSON пропали все
параметры, включая критичный `options.downloadAttachments: true` — без него узел не отдаёт
вложения дальше по цепочке, и весь пайплайн распознавания речи остался бы без аудио. Похоже, что
UI-форма для этого типа/версии узла не рендерит некоторые поля, и при сохранении из UI все
"невидимые" в форме параметры воспринимаются как значения по умолчанию и не сериализуются в JSON,
даже если они были явно выставлены ранее через API.

Как применять: после любого сохранения сценария через UI n8n (даже если пользователь менял вроде
бы только один несвязанный узел) — заново получить сценарий через `GET /api/v1/workflows/{id}` и
сверить параметры триггера/остальных узлов с ожидаемыми, а не полагаться на то, что
непотревоженные узлы остались как были. Если параметры пропали — восстановить через прямой
`PUT`-вызов API и сразу же перепроверить через `GET`, что значения действительно сохранились
(round-trip), а не доверять единственному ответу на PUT.

## Perr7.1 — n8n в docker-контейнере не видит 127.0.0.1 хоста; узнать реальный адрес можно эмпирически через реальный HTTP-узел
Локальный сервис на хосте (`127.0.0.1:8098`) был недоступен из HTTP Request node в n8n
("connection refused"/"the server is offline"), хотя с самого хоста (по SSH) сервис отвечал
нормально. Прямой способ проверки (`docker inspect` контейнера n8n на предмет `NetworkMode`) не
сработал — у выделенного SSH-пользователя не было доступа к Docker (`permission denied` на
`/var/run/docker.sock`), а `Execute Command`-узел в n8n оказался отключён на этом инстансе
(вероятно, специально из соображений безопасности — и локальный классификатор безопасности тоже
блокирует связку "публичный webhook + выполнение команд" на чужом/общем сервере, так что даже
если бы узел работал, так тестировать не стоило). В сумме это означало: нет прямого способа
узнать сетевые настройки контейнера, надо было выяснять эмпирически.
Рабочий способ: временно подставить в реальный сценарий (через уже существующий, легитимный
триггер — email, не публичный webhook) `HTTP Request`-узел с несколькими URL-кандидатами
(`host.docker.internal`, `172.17.0.1`, `172.18.0.1`, ...) и по разнице ошибок понять, что
происходит: `getaddrinfo`/`incorrect host` = имя не резолвится вообще, `connection refused` =
сеть до хоста доходит, но никто не слушает именно на этом адресе. Это быстро подсказало решение:
не хост недостижим, а наш собственный сервис слушал только `127.0.0.1` — после того как
переключили его на `0.0.0.0`, шлюз docker-моста (`172.17.0.1`) заработал.

Как применять: если n8n (или другой оркестратор) задеплоен в контейнере, а локальный сервис,
который он должен вызывать, живёт на том же физическом хосте — не считать по умолчанию, что
`127.0.0.1` сработает, даже если с самого хоста всё выглядит нормально. Если нет доступа к
`docker inspect`/`docker network`, можно определить рабочий адрес эмпирически: подставить
несколько адресов-кандидатов в реальный (не публично уязвимый) HTTP-узел и по типу ошибки понять,
на каком этапе рвётся связь — резолвинг имени или уже сам порт. И почти всегда локальный сервис,
который должен быть виден извне контейнера, придётся явно перевести с `127.0.0.1` на `0.0.0.0` —
в этом случае стоит сразу добавить простую защиту токеном/заголовком, раз порт становится видимым
шире, чем предполагалось изначально.

## Perr7.1 — синхронный тяжёлый код в async-обработчике FastAPI блокирует весь сервис целиком, включая health-check
Эндпоинт `/transcribe` вызывал `model.transcribe()` (faster-whisper) и `subprocess.run(ffmpeg)`
напрямую внутри `async def`-обработчика. Оба вызова синхронные и CPU-тяжёлые — они блокируют
единственный поток asyncio event loop целиком. Пока шла обработка одного файла, сервис не отвечал
вообще ни на что, включая простой `GET /health` — это выглядело как "сервис упал", хотя процесс
был жив и просто занят. На одном из тестовых файлов обработка неожиданно растянулась на 14+ минут
(вероятно, беглый цикл/зацикливание модели на конкретном фрагменте — похожая история уже была с
Ollama в Perr6.5), и всё это время сервис был полностью недоступен, а клиент (n8n) в итоге обрывал
соединение по своему таймауту, оставляя сервер молотить впустую.

Как применять: любой блокирующий/CPU-тяжёлый вызов (транскрибация, генерация, вызов внешнего
бинаря через `subprocess.run`) внутри async-обработчика FastAPI/Starlette оборачивать в
`asyncio.to_thread(...)`, а сверху — в `asyncio.wait_for(..., timeout=N)` с разумным жёстким
потолком. Это не ускоряет саму обработку, но: (1) не даёт одному медленному запросу полностью
парализовать сервис (health-check и другие запросы продолжают отвечать), и (2) гарантирует, что
клиент получит понятную ошибку по таймауту вместо вечного зависания. Отдельно стоит подстраховаться
от зацикливания декодера на маленьких CPU-моделях: простой `beam_size=1` без сложных доп. фильтров
(`vad_filter` и т.п.) обычно стабильнее, чем настройки по умолчанию.

## Perr8.1 — задание можно закрывать реальным внешним проектом, но отчёт должен явно замапить его на пункты задания
Задание 8.1 (Transfer Learning) было выполнено не учебным примером, а реальным
fine-tuning-проектом пользователя из другого репозитория (SINTARIS, дообучение Gemma через
QLoRA в Colab). Артефакты жили в трёх местах: код — в приватном рабочем репо, результаты

Как применять: при оформлении отчёта по внешнему проекту (1) скопировать в папку задания

(3) большие исходники (датасеты на гигабайты, презентации эксперта) не коммитить — добавить

«базовая предобученная без тюнинга vs дообученная» и объяснить это в отчёте со ссылкой на
слова самого урока (обучение BERT с нуля — неделя кластера).

## Perr7.1 — IMAP-триггер n8n может объединить несколько новых писем в одно выполнение, и один упавший item валит все остальные
При тестировании (письма с записями звонков отправлялись пачкой) n8n иногда забирал сразу
несколько новых писем в **одно** выполнение сценария (до 6 сразу), передавая их как отдельные
items по общему графу узлов. Если на каком-то узле без `continueOnFail` падает хотя бы один item
(например, конкретный файл слишком долго обрабатывается и превышает таймаут), падает **всё**
выполнение — ни один item, включая те, что уже успешно прошли до этого узла, не доходит до
записи в Google-таблицу. Внешне это выглядит как "все записи не обработались", хотя часть из них
по факту отработала нормально на предыдущих шагах.

Как применять: при отладке сценария, который принимает пачку писем/файлов, не считать, что "одно
письмо = одно выполнение" — реальное количество items в конкретном выполнении нужно смотреть в
самих данных (`runData` триггера), а не только по числу writes в источнике. Для чистой диагностики,
какой именно item/файл вызывает проблему, надёжнее прогонять их по одному с паузами (дождаться
завершения предыдущего перед отправкой следующего), а не пачкой. Для продакшна стоит явно решить:
либо разносить приём по времени, либо включать `continueOnFail`/`onError: continueRegularOutput`
на узлах, где сбой одного item не должен ронять всю пачку.

## Perr7.4 — при написании "демонстрационного" документа (задание решено не кодом, а разбором существующей системы) легко вписать правдоподобную, но выдуманную деталь
Готовился документ, показывающий, как задание про поиск резюме уже решено в реальном продукте
(Taris) — без нового кода, только текст с разбором реальных файлов/функций и реальных случаев из
документации проекта. В черновике одного абзаца (про то, почему английские фрагменты руководства
неожиданно попали в топ поиска по русскому вопросу) я дописал правдоподобно звучащее "объяснение"
причины (якобы совпадение по конкретному слову), которого не было в источнике — сам исходный
документ эту причину не называет, он лишь фиксирует факт. Заметил только при целенаправленной
повторной сверке черновика с оригиналом перед коммитом, а не по ошибке компиляции или тесту —
такое не ловится автоматически.

Как применять: когда результат задания — не работающий код, а **текст, объясняющий существующую
систему** (архитектурный разбор, демо-документ, sales-питч про свою же платформу), риск
"дописать логичное, но не подтверждённое источником объяснение" выше, чем в коде, потому что
текст не падает с ошибкой, если факт неверен. Для каждого конкретного технического утверждения в
таком документе (номер строки, точное поведение, причина бага, точный формат вывода) — перед
финальным коммитом отдельно свериться с первоисточником (реальный файл кода/строка, а не только
архитектурный `.md`-пересказ) и убрать любую формулировку, которая заполняет пробел в источнике
"на правдоподобии", а не на факте. Если причина явления в источнике не указана — так и написать
("случилось X", без "потому что Y"), а не придумывать правдоподобное Y.
