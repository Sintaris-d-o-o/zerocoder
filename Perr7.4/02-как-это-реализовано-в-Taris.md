# Как эта задача уже решена в Taris

Задание 7.4 просит собрать «поисковик по резюме»: по текстовому описанию вакансии находить
наиболее подходящих кандидатов среди множества резюме, используя эмбеддинги (числовые «отпечатки
смысла» текста) и векторную базу данных.

В голосовом ассистенте **Taris** (проект `sintaris-pl`) уже больше года работает технология того
же типа — она называется **RAG** (Retrieval-Augmented Generation, «поиск + генерация ответа»).
Разница только в предметной области: вместо «вакансия → резюме» там «вопрос пользователя о
здоровье/питании → нужный фрагмент базы знаний / товарного справочника». Сама технология — поиск
по смыслу среди множества документов через эмбеддинги и векторную базу — идентична.

Ниже — пошаговое сопоставление, что просит задание и где именно в реальном коде Taris это уже
сделано, плюс живые примеры из документации проекта (не выдуманные — они описаны в
`doc/architecture/knowledge-base.md` на основе реальных случаев работы бота).

## 1. Пайплайн задания → реализация в Taris

### 1.1 Подготовка среды

**Задание просит:** установить библиотеки для векторизации текста, базы данных, загрузки
документов и таблиц; проверить версии, чтобы не ловить сюрпризы от обновлений.

**В Taris:** зависимости зафиксированы в `deploy/requirements.txt` / `src/setup/*.sh`
(`sentence-transformers`, `fastembed`, `psycopg2-binary`, `pgvector`, `PyMuPDF`, `python-docx` —
таблица в `doc/architecture/stacks.md`). Библиотека эмбеддингов подключается «мягко»: класс
`EmbeddingService` (`core/bot_embeddings.py`) сам пробует `fastembed`, при неудаче —
`sentence-transformers`, и если ни одна не доступна — не падает, а просто отключает семантический
поиск (`core/bot_embeddings.py:105-144`, метод `_try_load`). Отдельный скрипт
`setup/install_embedding_model.sh` заранее скачивает и проверяет модель на целевом устройстве.

### 1.2 Модель эмбеддингов для русского языка (бесплатная)

**Задание просит:** перевести текст в векторный формат с помощью бесплатной модели эмбеддингов
для русского языка.

**В Taris:** ровно то же самое — модель по умолчанию:

```python
# core/bot_config.py:431-432
EMBED_MODEL = os.environ.get("EMBED_MODEL",
                   "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")
```

Это открытая многоязычная модель (384-мерный вектор), понимает русский, работает локально без
интернета и без единого API-ключа. В `core/bot_rag.py:558-567` есть комментарий с реальными
калибровочными цифрами: даже для нерелевантных русских запросов эта модель даёт оценку схожести
≈0.25–0.36, поэтому порог отсечения «мусорных» результатов специально откалиброван под неё
(0.20) — это как раз тот самый практический опыт, который упражнение в Colab обычно не
затрагивает, а в проде вылезает сразу.

### 1.3 Загрузка «базы» и работа со структурой данных

**Задание просит:** загрузить базу резюме, посмотреть первые строки, определить уникальные
значения ключевых колонок, оставить нужные колонки, преобразовать таблицу в текст.

**В Taris** роль «базы резюме» играет **база знаний**: загруженные пользователем документы
(PDF/DOCX/TXT/RTF — `features/bot_documents.py`) плюс готовый товарный справочник (например,
«Справочник по продукции LR и нутрициологии Алоэ Вера»). Административная панель показывает
список документов ровно как «просмотр первых строк базы»: заголовок, число чанков, число токенов,
дата, превью текста (`_kb_list_documents_direct()` в `core/bot_mcp_client.py`; аналог в
`features/bot_remote_kb.list_docs()`).

**Самое буквальное совпадение с пунктом «преобразуй таблицу в текст»** — функция
`_flatten_tables()` в `features/bot_documents.py`. Товарный справочник LR — это таблицы
(«состояние → продукт», характеристики товаров), и при обычном чанкинге текста заголовок таблицы
и её строки часто попадают в разные блоки — модель теряет, какая колонка что означает.
`_flatten_tables()` (`features/bot_documents.py:238`) переписывает каждую строку markdown-таблицы
в самостоятельный блок текста, где однострочная выжимка идёт первой, а каждое подписанное значение
повторяет ключ строки — именно то, что просит задание («преобразуй таблицу в текст»), только
сделано не вручную в ноутбуке, а автоматически при каждой загрузке/переиндексации документа
(описано в `doc/architecture/knowledge-base.md:406-445`, с реальным разбором дефекта: до этой
функции вопрос о здоровье женщин отвечался колонкой «синергисты» соседнего товара, потому что
заголовок таблицы оторвался от строк при нарезке на чанки).

### 1.4 Разбить текст на блоки (чанки) и превратить в документы

**Задание просит:** разбить текст на блоки и преобразовать их в документы для поиска.

**В Taris:** `_chunk_text()` (`features/bot_documents.py:383-443`). Правило — «чанк никогда не
разрывает заголовок» (текст сначала делится по структуре документа, потом каждый раздел
упаковывается отдельно), и «каждый чанк несёт свой путь заголовков» (документ → глава → раздел),
иначе фрагмент текста, вырванный из контекста, не с чем сопоставить. Размер блока — константа
`RAG_CHUNK_SIZE = 512` символов (`core/bot_config.py:441`); фрагменты короче 20 символов
(`_MIN_CHUNK_CHARS`, `features/bot_documents.py:134`) отбрасываются как «мусор» (номера страниц,
обрывки навигации) — это и есть контроль качества данных, аналог «доработай и проверь результат»
из задания.

### 1.5 Построить векторную базу данных

**Задание просит:** построить векторную базу данных для поиска похожих по смыслу фрагментов.

**В Taris** — две реализации в зависимости от «железа» (в задании этого нет, но это ровно тот
практический вопрос, который встаёт сразу после учебного примера — «а что если база большая и
работает не в облаке, а на слабом компьютере»):

| Платформа | Векторная БД | Файл |
|---|---|---|
| Raspberry Pi (слабое железо) | `sqlite-vec` — векторный поиск прямо внутри SQLite, 384-мерные векторы | `core/store_sqlite.py:705` (`search_similar`) |
| Сервер | PostgreSQL + `pgvector` | `core/store_postgres.py`, `core/bot_mcp_client.py` (`_kb_search_direct`) |

Поиск — косинусное сходство через KNN-запрос к векторной таблице (`store_sqlite.py:705-735`):
запрашивается с запасом (`top_k * 6`), затем в Python отфильтровываются чужие/неразрешённые
документы и дубликаты.

### 1.6 Настроить поиск и структурировать вывод

**Задание просит:** настроить поиск и доработать вывод, чтобы результат был структурирован и
понятен.

**В Taris** это самая развитая часть — `core/bot_rag.py`, функция `retrieve_context()`:

- **Классификация запроса** (`classify_query()`, `bot_rag.py:145-175`) — короткое приветствие не
  запускает поиск вообще, вопрос с фактическим содержанием — запускает.
- **Гибридный поиск** — текстовый (BM25/FTS5) и векторный поиск выполняются параллельно, потом
  объединяются алгоритмом **Reciprocal Rank Fusion** (`reciprocal_rank_fusion()`,
  `bot_rag.py:233-278`, `score = Σ 1/(k + rank)`, k=60) — это честный способ сказать «доверяем
  обоим методам поиска, а не одному».
- **top_K и структура ответа** — `RAG_TOP_K = 16` (`core/bot_config.py:440`, поднято с 3 в
  несколько итераций по мере реальных проблем с обрезкой релевантных результатов — в коде прямо
  записана история этого решения).
- **Итоговый структурированный вывод** — `features/bot_remote_kb.py` (функция поиска, ~строка
  1460): найденные фрагменты собираются в контекст с номером и разделом, LLM формирует ответ
  **только на основе найденного** (не «от себя»), и в конце добавляется подпись с источниками —
  «📚 *Sources*:» и построчный список вида «• Название документа (номер) — §раздел1, §раздел2».
  Это прямой аналог «результат должен быть структурирован и понятен» из задания: пользователь
  получает не просто «похожие резюме», а готовый ответ + видит, на основании чего он получен.

## 2. Живой пример из продакшена

Ниже — реальный, уже зафиксированный в документации Taris случай (не придуманный для демонстрации),
показывающий весь пайплайн в действии.

**Вопрос пользователя:** «у меня болят суставы, что делать?»

**Что должен найти поиск:** товары для суставов — Фридом, Эктив Фридом, глюкозамин, хондроитин.

**Что произошло без нужной настройки (зафиксировано как дефект, потом исправлено):** после правки
и переиндексации служебного руководства бота (оно на английском) шесть его фрагментов неожиданно
оказались на первых местах текстового поиска именно по этому русскому вопросу — заняли лучшие
позиции ещё до того, как их успевали отфильтровать как «не тот источник». А поскольку фильтр по
источникам («это руководство, а не товарная база — не показывать») применялся только **после**
объединения результатов поиска, к этому моменту нужные товары для суставов уже были вытеснены за
пределы топ-16 — их отбросило не ранжирование и не изменения в самом товарном каталоге, а именно
порядок шагов пайплайна. Расширение зоны поиска (взять не топ-16, а втрое больше кандидатов) не
помогало: «лишние» фрагменты стояли не в хвосте списка, а на самых первых местах.

**Как это устроено в решении** (`doc/architecture/knowledge-base.md:158-179`): у каждого документа
есть «группа» (`guides` — служебная документация, `knowledge` — товарная база), и фильтр по группе
применяется **до** объединения результатов поиска, а не после — иначе «лишний» документ уже успел
бы занять топовые места и вытеснить нужный товар, даже если его потом отфильтруют.

**Второй пример** (`knowledge-base.md:449-478`) — вопрос «какой состав супер омега ЛР»: нужная
страница товара оказалась лучшим текстовым совпадением (score 0.746 и 0.689 — первое и второе
место), но из-за особенностей объединения результатов («демократии» алгоритма RRF) итоговая
позиция после слияния — 17-е и 19-е место, за пределами топ-16. Решение: «лексические якоря»
(`RAG_LEXICAL_ANCHORS`) — лучшие текстовые совпадения принудительно поднимаются в начало списка,
а не просто участвуют в общем ранжировании наравне со всеми.

Оба примера показывают то, о чём Colab-версия задания обычно не говорит: **построить поиск —
полдела, довести его до того, чтобы он реально находил нужное на реальных данных — вторая
половина**, и именно там в Taris накоплен год практического опыта.

## 3. Чем техническая реализация отличается от условий урока

| | В задании (Google Colab) | В Taris |
|---|---|---|
| Модель эмбеддингов | любая, обычно через `sentence-transformers` из HuggingFace Hub | та же библиотека, конкретная модель `paraphrase-multilingual-MiniLM-L12-v2` — выбрана за поддержку русского и малый размер (работает на Raspberry Pi) |
| Векторная база | обычно Chroma/FAISS (облачный ноутбук, диск не ограничен) | `sqlite-vec` (слабое железо) или `pgvector` (сервер) — выбор зависит от целевого устройства |
| Совмещение методов поиска | как правило, один векторный поиск | гибрид: текстовый (BM25) + векторный, объединяются через RRF — надёжнее на коротких/неполных запросах |
| Где работает | Google Colab, требует интернет на каждый запуск | локально на устройстве пользователя (Raspberry Pi, ноутбук или сервер), офлайн после разовой загрузки модели |
| Итоговый ответ | обычно список найденных строк таблицы | связный ответ от LLM на основе найденного + список источников |

Это ожидаемое и осознанное отличие: учебное задание рассчитано на разовый эксперимент в
блокноте, а Taris — на круглосуточную работу на слабом железе без постоянного доступа к
дорогим облачным сервисам, отсюда и другой выбор инструментов при той же сути задачи.

## 4. Где это можно увидеть своими глазами

- **В самом ответе бота** — под ответом на вопрос по базе знаний есть подпись «Sources: …» с
  разделами документов, откуда взята информация.
- **Admin Panel → 🔍 RAG / Knowledge Base → 📊 RAG Stats** — статистика по всем запросам:
  среднее число найденных фрагментов, среднее время поиска, разбивка запросов по типу
  (простой/фактический/контекстный), топ-5 самых частых запросов
  (`store_sqlite.rag_stats()`, `telegram/bot_admin._handle_admin_rag_stats()`).

Оба пункта — это и есть тот самый «структурированный и понятный вывод», который просит задание,
только увиденный не в ячейке Colab-ноутбука, а в работающем продукте.
