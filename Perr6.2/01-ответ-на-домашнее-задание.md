## 3. Разбор кода

Ноутбук устроен как **три версии одного и того же бота, с нарастающей сложностью** — это и есть главная методическая ценность примера: не «вот готовое решение», а «вот как его пошагово улучшать».

### Версия 1 — простой RAG на чистом LangChain

Документы из Notion грузятся в векторную базу Chroma, дальше — классическая связка «найти похожие документы → подставить в промпт → спросить модель»:

```python
vector_store = Chroma.from_documents(
    documents=data_processed,
    embedding=OpenAIEmbeddings(),
)
retriever_from_notion = vector_store.as_retriever(search_kwargs={"k": 5})

prompt = ChatPromptTemplate([
    ("system",
     "You are a helpful assistant for onboarding new employees.\n"
     "Please answer the question based on the following documents.\n"
     "Documents: \n{context}"),
    ("human", "{question}"),
])

langchain_only_rag_chatbot = (
    {
        "question": RunnablePassthrough(),
        "context": retriever_from_notion | context_parser,
    }
    | prompt
    | llm
)
```

Авторы сразу честно называют проблему этой версии: «retrieved documents may appear similar to the query but are not always semantically relevant» — похожий по формулировке документ не значит правильный документ.

### Версия 2 — фильтрация релевантности через LangGraph

Добавляется узел графа, который для каждого найденного документа отдельным вызовом модели спрашивает «да/нет, этот документ относится к вопросу?», и в промпт для ответа идут только документы с «да»:

```python
def filter_relevant_docs_node(state: RetrievalState) -> RetrievalState:
    question, docs = state["question"], state["retrieved_docs"]
    is_each_docs_relevant_chain = RunnableParallel({
        str(idx): {"question": RunnablePassthrough(), "context": ...}
        | prompt_relevance_check | llm | StrOutputParser()
        for idx, doc in enumerate(docs)
    })
    # оставляем только документы, где модель ответила "yes"
    ...
```

Важное наблюдение из кода: проверка релевантности запускается **параллельно по всем найденным документам** (`RunnableParallel`), а не последовательно — иначе фильтрация была бы в разы медленнее.

Ключевая архитектурная деталь — граф LangGraph подключается в обычную LCEL-цепочку как один из шагов, а не как отдельная изолированная программа:

```python
langgraph_applied_rag = (
    {
        "question": RunnablePassthrough(),
        "context": {"question": RunnablePassthrough()}
        | langgraph_retriever
        | RunnableLambda(lambda result: result["relevant_docs"])
        | context_parser,
    }
    | prompt | llm | StrOutputParser()
)
```

### Версия 3 — разбиение сложного вопроса на подвопросы

Реальные вопросы пользователей редко бывают аккуратно сформулированы одним предложением. Добавляется ещё один узел-агент, который сначала разбивает вопрос на несколько простых подвопросов, каждый подвопрос параллельно проходит через весь пайплайн версии 2 (поиск → фильтр → ответ), а в конце отдельный шаг сводит все частичные ответы в один связный:

```python
def split_question_node(state: QuestionState) -> QuestionState:
    response = (prompt_split_question | llm | StrOutputParser()).invoke({"question": state["question"]})
    sub_questions = response.split("\n") if "\n" in response else [response]
    return {"question": state["question"], "sub_questions": sub_questions}

chat_bot = (
    {
        "question": RunnablePassthrough(),
        "sub_answers": {"question": RunnablePassthrough()}
        | langgraph_question_splitter
        | RunnableLambda(lambda r: list_to_dict(r["sub_questions"]))
        | dict_to_dynamic_runnable(langgraph_applied_rag)   # версия 2 целиком, запущенная параллельно на каждый подвопрос
        | RunnableLambda(lambda r: list(r.values())),
    }
    | prompt_summarize_sub_answers | llm
)
```

Проверил на примере из ноутбука — вопрос сразу про две разные темы («как проверить остатки на складе» + «как оформить запрос в отдел операций»): бот сам разбивает его на два подвопроса, отвечает на каждый отдельно и через базу знаний, а затем собирает один итоговый ответ.

## 4. Как применю в своём проекте (Тарис)

Схема переносится на Тарис почти без изменений — меняется только источник знаний и формулировка промптов:

```
Онбординг-бот Тариса
 1. База знаний в Notion/Google Docs: правила платформы, инструкции для экспертов
    (как загрузить курс, настроить выплаты), FAQ для студентов (расписание, доступ к урокам)
 2. Версия 1: обычный RAG-бот отвечает на вопросы новых пользователей
 3. Версия 2: фильтр релевантности — чтобы бот не путал похожие, но разные темы
    (например, вопрос "как загрузить видео урока" не должен отвечаться документом
    про загрузку обложки курса, даже если оба документа про "загрузку")
 4. Версия 3: разбиение сложных вопросов — новый эксперт часто пишет
    "как настроить выплаты и куда грузить материалы и видны ли черновики студентам?"
    одним сообщением — бот разбивает на 3 подвопроса и отвечает по каждому
```

Практическая ценность для Тариса именно в **инкрементальности** этого примера: можно запустить версию 1 буквально за день (минимальный RAG поверх текущей базы знаний платформы), а версии 2 и 3 подключать позже, когда станет видно, что бот путает похожие документы или не справляется с длинными вопросами — не нужно сразу проектировать сложную систему.

## 5. Наблюдения

- **Прогрессия сложности как метод обучения и как метод разработки.** Ноутбук специально построен так, чтобы показать: «агентность» — это не бинарный выбор (простой RAG или сложный агент), а шкала, по которой можно двигаться постепенно, добавляя по одному узлу графа за раз, не переписывая всё с нуля. Для Тариса это значит: можно закладывать в архитектуру бота с самого начала точки расширения (фильтрация, декомпозиция), но не реализовывать их сразу.
- **LangGraph не заменяет LangChain, а встраивается в LCEL-цепочку как обычный шаг** (`langgraph_retriever` используется внутри `{...} | prompt | llm` наравне с любым другим `Runnable`). Это снижает порог входа — не нужно переписывать весь пайплайн под новую парадигму, чтобы добавить агентное поведение в один конкретный шаг.
- **Спорная находка в самом коде примера:** токен доступа к Notion зашит прямо в ячейку ноутбука открытым текстом:
  ```python
  NOTION_TOKEN = "ntn" + "_L3541776489aPP4RRULRr1dAfxDeeeBoJUufhX8ON0y4tM"
  ```
  Даже разделение строки на две части похоже на попытку обойти автоматическое сканирование секретов на GitHub. Это учебный демо-токен к публичной тестовой базе, а не чья-то реальная утечка, но сама практика — ровно то, чего в проекте Тарис делать нельзя: у нас правило «все credentials — только в `.env`», и этот пример из чужого кукбука на практике показывает, зачем оно нужно.
- **Фильтрация релевантности — это отдельный вызов LLM на каждый найденный документ.** Удобно и повышает точность, но при базе знаний в сотни документов и `k=5` это будет 5 дополнительных запросов к модели на каждый вопрос пользователя — для Тариса стоит сразу закладывать это в оценку стоимости бота, а не выяснять постфактум по счёту за API.
