# Выдержки из документации сервера dev2null.de

Источник: закрытый репозиторий администрирования серверов `sintaris-srv`
(`vps-admin/docs/`). Проверяющему он недоступен, поэтому нужные строки скопированы сюда
(журнал переведён с немецкого, номера записей сохранены). Паролей, ключей и IP-адресов здесь нет.

Это тот же VPS, на котором выполнялись задания курса 7.1 (сервис распознавания речи) и
10.5 (запуск `main.py` «с чужой машины»).

---

## 1. Параметры сервера

Из `06-vps-dev2null.de.md` и `09-vps-software-deployment.md`:

| Свойство | Значение |
|---|---|
| Провайдер | Netcup (Германия) |
| Система | Ubuntu 24.04 LTS, процессор ARM (aarch64) |
| CPU | 6 ядер |
| Память | 7,7 ГБ, плюс 8 ГБ файла подкачки |
| Диск | 504 ГБ |
| Занято памяти в работе | 2,7 ГБ (ещё 5,4 ГБ — кэш файлов, система отдаёт его по требованию) |
| SSH | только по ключу, пользователь `stas`; для `root` — `PermitRootLogin no` |
| Автоматические обновления | `unattended-upgrades` включены |

Что на нём работает: nginx, почта (postfix, dovecot), PostgreSQL, MySQL, n8n
(`automata.dev2null.de`), Nextcloud, ассистент Taris и Telegram-боты в Docker,
защита от перебора паролей fail2ban.

## 2. Python-сервис из задания 7.1 найден на сервере при аудите

Журнал, запись 186 (аудит программ на сервере, конец августа 2026):

> `perr71-stt` (`0.0.0.0:8098`, `/home/inna/perr71-stt/`) работает **без службы systemd**:
> после перезагрузки сервиса не будет.

То есть сервис, запущенный в задании 7.1 командой `nohup … &`, продолжал работать спустя
недели после закрытия терминала. Замечание аудита честное: `nohup`, как и `screen`, не
переживает перезагрузку сервера.

## 3. Обновления: что показал аудит безопасности

Журнал, запись 149 (28.08.2026, только чтение):

> Анализ безопасности: доступно **129 обновлений, из них 11 — обновления безопасности**,
> **перезагрузка просрочена** (установлено 3 новых ядра, сервер работает 23 дня без перезагрузки),
> SSH принимает пароли, на самом сервере нет файрвола.

Урок 80 из `vps-coding-protocol.md`: *«`unattended-upgrades` ставит новое ядро, но сам сервер
не перезагружает»*. Признак, что перезагрузка нужна, — файл `/var/run/reboot-required`.
После этого в мониторинг сервера добавлена ежедневная проверка обновлений безопасности.

## 4. Вход по SSH: как закрывали вход по паролю (11.09.2026)

Журнал, записи 209–220:

| № | Что сделано |
|---|---|
| 209 | **Взлома не было.** Успешные входы только у `stas` по ключу и у контейнера n8n. 8 766 неудачных попыток, ни одной удачной |
| 210 | Распределённый перебор паролей: 872 блокировки fail2ban за день при обычных 50–77, адреса из десятков стран, то есть ботнет |
| 211 | Перебор частично прицельный: кроме `ubuntu` и `crypto` пробовали `sintaris` (218 раз) и `sintaru` (108) |
| 212 | Главная дыра: SSH принимал пароли для всех, а у двух старых учётных записей с правами администратора не было ключей, только пароли |
| 214 | Перед изменением сохранены копии `sshd_config`, `50-cloud-init.conf` и `/etc/shadow` |
| 216 | Вход по паролю из интернета закрыт. Править пришлось **три места**, потому что у SSH **побеждает первая** найденная настройка: файл `sshd_config.d/50-cloud-init.conf` подключается в строке 18 и разрешал пароль, перекрывая запрет в строке 130. Для контейнера n8n пароль оставлен только из внутренней сети Docker |
| 217 | До применения проверено командой `sshd -T -C` для разных адресов: снаружи пароль запрещён, для n8n разрешён, для своего адреса только ключ |
| 218 | `systemctl reload ssh` (а не `restart`), чтобы не оборвать открытые сеансы |
| 219 | Проверка: вход по ключу работает, попытка входа по паролю снаружи даёт `Permission denied (publickey)` |
| 220 | n8n после изменения подключается как раньше |

Урок 128 из `vps-coding-protocol.md`: *«Три попытки ввести пароль из WinSCP заблокировали
(fail2ban) домашний адрес, а с ним оба туннеля к домашнему серверу. Правило: не пробовать
вход по паролю на dev2null.de; входить по ключу, аварийный доступ — через консоль Netcup»*.
