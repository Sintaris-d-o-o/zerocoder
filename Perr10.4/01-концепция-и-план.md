# Задание 10.4 — концепция и план

## Что просят

Превратить скрипт генерации видео в продукт с двумя интерфейсами и развернуть на сервере:

1. **Telegram-бот** — приём промпта, запуск генерации, прогресс со статусами, отправка видео,
   обработка ошибок. Отдельные требования: бот не генерирует при импорте
   (`if __name__ == "__main__"`) и **обновляет одно сообщение**, а не шлёт новые.
2. **Сайт на Flask** — поле ввода, кнопка, прогресс, скачивание. Идентификатор задачи через
   UUID, работа в потоках, маршруты `/generate`, `/status/<task_id>`, `/download/<task_id>`.
   Скачивание должно работать и после обновления страницы.
3. **Развёртывание** — GitHub, SSH, виртуальное окружение, запуск бота и сайта в `screen`,
   `host='0.0.0.0'`, `debug=False`, процессы живут после закрытия сессии.

Отчёт: скриншоты бота и переписки, сайта, страницы скачивания, `screen -ls`, репозитория;
ссылка на GitHub; описание архитектуры в 5–10 предложений.

## Главное: это задание уже решено в нашем продукте

Задание описывает ровно ту задачу, которую платформа **Taris** решает в продакшне: одно ядро
и два интерфейса поверх него. Это не теория — система работает на девяти экземплярах, включая
`certtaris`, обслуживающий наш же кейс с сертификатами.

Сразу поправка по названию: папка `sintaris-openclaw` содержит **не** одноимённый шлюз на
Node.js, а репозиторий Taris (`sintaris-pl`). Настоящий OpenClaw — другой проект.

Что там есть по каждому пункту задания:

| Требование задания | Как решено в Taris |
|---|---|
| Telegram-бот принимает запрос | `src/telegram_menu_bot.py`, 3 556 строк, библиотека pyTelegramBotAPI. Всего **11 обработчиков**: шесть команд, один маршрутизатор кнопок и четыре типа содержимого (текст, голос, фото, документ) |
| **Обновлять одно сообщение**, а не слать новые | Это канонический приём платформы: показать «печатает», отправить заглушку «⏳ Думаю…», запустить работу в потоке и в конце **заменить текст этого же сообщения** через `edit_message_text`, с двухуровневым запасным вариантом, если разметка не прошла |
| Прогресс со статусами | На вебе — фоновый поток плюс опрос состояния из браузера; в голосовом режиме подпись проходит по стадиям: распознавание → модель → синтез речи |
| Сайт с полем ввода и кнопкой | `src/bot_web.py`, 16 255 строк, FastAPI и Jinja2 с HTMX, **271 маршрут**, 50 шаблонов |
| Идентификатор задачи, потоки, опрос статуса | Пересборка базы знаний: работа уходит в поток, состояние живёт в памяти, браузер опрашивает отдельный маршрут. В комментарии записана причина: пересчёт документа на 1 600 фрагментов занимает около 40 секунд и иначе держал бы запрос открытым дольше любого разумного таймаута |
| Отдача файлов пользователю | Загрузка с проверкой типа и размера, блокировка на пользователя; выгрузка с заголовком вложения и проверкой, что файл принадлежит запросившему |
| Развёртывание, работа 24/7 | **systemd**, а не `screen`: `taris-web` и `taris-telegram` — отдельные службы, обе с ограничением памяти и перезапуском при сбое. Снаружи публикуются через обратный туннель и nginx по своему подпути |

**Ключевая находка для отчёта.** Веб и Telegram у вас — не две копии логики, а два «рисовальщика»
поверх общей середины. Измеренный факт: **24 модуля импортируются обоими** входными точками,
общий слой (ядро, функции, интерфейсные описания) — около 47 тысяч строк. Есть даже язык
описания экранов: экран пишется один раз, а рисуется отдельно для Telegram и отдельно для
браузера.

И ещё одно, прямо про задание: **новый экземпляр — это настройка, а не код**. `certtaris`
подняли web-only, а Telegram-бота добавили через две недели: выдали свой токен и сняли флаг
«только веб». Никакого ветвления кода.

## Что делаем

Две части, дополняющие друг друга.

### Часть А — учебная реализация (закрывает буквальные требования)

Оборачиваем генератор видео из задания 10.3 в бота и сайт. Почти всё уже готово:

- **Сайт** собирается из приложения задания 10.2 — там уже есть UUID задачи, фоновые потоки,
  маршруты запуска, опроса статуса и скачивания, страница с прогрессом. Меняется источник:
  вместо картинки — видео из 10.3.
- **Бот** пишется с нуля, около 200 строк, по приёму из Taris: заглушка, поток, замена текста
  того же сообщения.

### Часть Б — как это устроено у нас в продакшне

Документ, показывающий на реальных числах, как решены те же задачи в Taris: разделение ядра и
интерфейсов, долгая работа вне запроса, прогресс в обоих каналах, отдача файлов, развёртывание.

Отдельный раздел — **почему systemd, а не screen**, как предлагает урок. Причина проста:
`screen` не переживает перезагрузку сервера, служба поднимается сама. В уроке `screen` взят для
простоты, и это стоит назвать своим именем.

## План работ

1. `video_web.py` — сайт на Flask для генератора видео (на основе 10.2).
2. `video_bot.py` — Telegram-бот с обновлением одного сообщения.
3. Тесты без обращения к платному сервису: маршруты, статусы, потоки, разбор команд бота.
4. Прогон: генерация через сайт и через бота, скриншоты.
5. Документ по архитектуре Taris с измеренными числами.
6. `результаты.md` со сверкой по трём частям, `demo.md`, текст для формы.

## Что нужно решить

1. **Токен бота.** Для учебной части нужен свой бот через BotFather, токен в `.env`
   (`TELEGRAM_BOT_TOKEN`). Заводить новый или взять существующий тестовый?
2. **Развёртывание.** Урок требует `screen` на сервере и скриншот `screen -ls`. Варианты:
   поднять учебную пару на вашем сервере в `screen` ради буквального соответствия, либо
   показать боевое развёртывание Taris через systemd и объяснить разницу. Рекомендую второе
   как основу и первое — если нужен именно скриншот `screen -ls`.
3. **Скриншоты продакшна.** Показывать ли в отчёте настоящий `certtaris` (веб и бот) или
   ограничиться учебной парой. Настоящий выглядит убедительнее, но это ваш рабочий продукт.

## Бюджет

Генерация видео платная. На счету RouterAI осталось 43,8 кредита — это один ролик. Для
скриншотов бота и сайта хватит: в тестах генерация подменяется, а для живой демонстрации
достаточно одного запуска. При необходимости можно показать процесс на уже готовом ролике
из задания 10.3.
