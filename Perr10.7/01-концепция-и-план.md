# Задание 10.7 — концепция и план

## Что просят

Веб-сервис прескоринга кандидатов:

1. **Анализ резюме** — ключ в `.env`, строгий JSON с полями `score`, `strengths`,
   `weaknesses`, `missing_skills`, `summary`, плюс «ремонт» JSON, если модель ответила криво.
2. **Разбор PDF** — `pdfplumber`, очистка текста, ограничение ~6000 знаков.
3. **Оценка** — раздельно hard skills / опыт / soft skills, настраиваемые веса (сумма 100%),
   итоговый балл по взвешенной формуле.
4. **Интерфейс** — Streamlit: текст вакансии, загрузка PDF, имя кандидата, итоговый балл,
   сильные и слабые стороны.
5. **История** — сохранение в JSON или CSV, сравнение нескольких кандидатов.

## Что у нас уже есть по этой теме

Вы просили проверить, есть ли в Taris агент для сканирования и подбора резюме.
**В Taris его нет** — я проверил весь `sintaris-pl` и соседние ветки, а также ботов
`universal-tgrm-bot`. Слово «резюме» там встречается только в значении «краткий пересказ»
(«Сделай резюме этого текста»), к подбору персонала отношения не имеет.

**Но такой агент у вас есть — и он работающий.** Это **N3 HR Assistant**, цепочка n8n из
27 узлов, сделанная в третьем задании курса: `zerocoder/N3/workflows/n3-hr-assistant.workflow.json`.

```
Gmail (письмо с резюме) → Extract PDF Text → Extract Candidate Info (gpt-4o)
  → Parse Candidate JSON → Get Vacancies (Google Sheets) → Prepare Matching
  → Run Matching (gpt-4o) → Parse Matching Result
  → Save Candidate (Sheets) → Has Match? → приглашение или отказ письмом
```

Что из него напрямую годится для 10.7:

| Что нужно в 10.7 | Что уже есть в N3 |
|---|---|
| Строгий JSON из модели | извлечение 13 полей кандидата, `response_format: json_object`, `temperature 0.1` |
| Оценка 0–100 | готовая рубрика: роль 40, скиллы 30, опыт 10, занятость 5, локация 5, зарплата 5, прочее 5 |
| Пороги для решения | ≥60 — подходит, 45–59 — почти, <45 — нет |
| Сильные и слабые стороны | в JSON мэтчинга есть `reasons[]` и `risks[]` для каждой вакансии |
| Нормализация должностей | свёртка семейств (frontend/backend/fullstack/mobile/devops/data/qa), транслитерация, синонимы |
| Разбор PDF | узел n8n `extractFromFile` |

Чего в N3 нет и что придётся делать заново: веб-интерфейс (там вход — почта), `pdfplumber`
(там разбор внутри n8n), раздельные веса hard/experience/soft с ползунками и история
сравнений в файле.

В папке задания лежит **`prescore-main.zip`** — эталонная реализация из урока: Streamlit,
`pdfplumber`, Pydantic, цепочка «ремонта» JSON. Её можно взять как отправную точку, но у неё
есть слабое место: она **не просит у модели JSON-формат** и поэтому чинит ответ четырьмя
последовательными функциями. Проще попросить строгий формат сразу, как это сделано в N3.

## Что предлагаю сделать

Собрать сервис на нашей теме и на нашей рубрике:

1. **Домен — наш.** Вакансии не абстрактные, а те, что нужны SINTARIS: специалист по
   регуляторным вопросам медизделий (RA), инженер по качеству (QA/ISO 13485), технический
   писатель для технических файлов MDR. Резюме для проверки — обезличенные, без реальных
   персональных данных.
2. **Оценка — двойная**, как в эталоне: детерминированный расчёт по ключевым словам и годам
   опыта плюс оценка модели, и итог как взвешенная смесь. Это честнее, чем доверять одной
   модели: детерминированная часть не меняется от запуска к запуску и её можно объяснить.
3. **Рубрика — из N3**, адаптированная под три группы весов из задания: hard skills,
   опыт, soft skills.
4. **Строгий JSON сразу** — `response_format`, а «ремонт» оставить как запасной путь: он
   нужен, потому что не все модели поддерживают формат.
5. **Модель — дешёвая.** Для прескоринга хватит `gpt-4o-mini` или `gpt-5-mini`; посчитаю
   стоимость одного резюме и напишу её в отчёт.
6. **История** — JSON-файл, таблица сравнения кандидатов, выгрузка.

## Польза для продукта

Прямой пользы для certtaris здесь нет: подбор персонала — не наш домен, и тащить его в
платформу не нужно. Поэтому делаем **отдельное учебное задание**, как вы и просили в таких
случаях.

Косвенная польза есть, и её стоит назвать: извлечение структурированного JSON из PDF по
заданной схеме — это ровно то, что certtaris делает с сертификатами и техническими файлами.
Если по ходу задания получится аккуратный разбор «PDF → строгий JSON → взвешенная оценка»,
его можно будет перенести на проверку комплектности технического файла MDR. Это предложение,
а не часть задания.

## План работ

1. `parser.py` — `pdfplumber`, очистка, предел 6000 знаков.
2. `scoring.py` — детерминированная часть и веса; рубрика из N3.
3. `gpt_service.py` — строгий JSON, запасной «ремонт», модель из `.env`.
4. `app.py` — Streamlit: вакансия, PDF, имя, итог, сильные и слабые стороны, история.
5. Тесты: разбор PDF, ремонт кривого JSON, арифметика весов, границы порогов.
6. Тестовые данные: три вакансии SINTARIS и несколько обезличенных резюме.
7. `результаты.md`, `demo.md`, скриншоты.

## Что нужно решить

1. **Где запускать.** Локально на ноутбуке (просто, но проверяющий не зайдёт) или рядом с
   n8n на SintAItion по адресу вида `prescore.sintaition.sintaris.net` (как 10.5 и 10.6 —
   тогда проверяющий откроет ссылку в браузере). Рекомендую второе: инфраструктура уже есть.
2. **Резюме для проверки.** В папке N3 лежат настоящие резюме трёх людей — их брать
   **не стоит**: это персональные данные, а отчёт уходит проверяющему. Предлагаю сгенерировать
   три-четыре обезличенных резюме под наши вакансии.
3. **Модель.** Дешёвая (`gpt-4o-mini`) или та же, что в N3 (`gpt-4o`, дороже, но рубрика
   отлаживалась на ней).
